## Review AppSec del control plane Web/API — 2026-11-04

Audit mirato (AppSec + Red/Blue) delle superfici a più alto rischio di un tool di sicurezza
professionale: l'API autenticata (`themis/api.py`) e il control plane Web (`themis/web.py`).
**Esito: nessuna vulnerabilità sfruttabile.** Checklist verificata:

**API (`themis/api.py`)**
- **Authz per endpoint:** ogni endpoint dati/azione dichiara una dipendenza di **scope**
  (`authenticated("<scope>")`): autenticazione via header API-key **o** OIDC bearer, poi
  `403` se l'identità non ha lo scope richiesto. Scope distinti per capacità
  (`capabilities:read`, `jobs:read/write/cancel`, `apollo:read/run`, …).
- **Unico endpoint aperto:** `/health` (stato/versione statici, nessun dato). `/ready` e
  `/metrics` (Prometheus) sono **dietro auth** (`reads_capabilities`).
- **OIDC:** bearer ostili sempre normalizzati a errore (property test esistente
  `test_themis_oidc`), mai eccezione non gestita.

**Web (`themis/web.py`)**
- **Rendering:** FastAPI `Jinja2Templates` con **autoescape attivo**; nessun `| safe`,
  `Markup` o `autoescape false` nei template (solo `<script src>` statici, nessuna
  interpolazione di variabili in script) → XSS mitigato.
- **Sessione:** cookie firmato, `HttpOnly` + `Secure` + `SameSite=Strict`, emesso solo da
  una credenziale API valida; `_require_session` protegge le pagine.
- **CSRF:** token sincronizzatore HMAC legato alla sessione, verificato in tempo costante
  (`hmac.compare_digest`) su **tutte le 11** route `POST` che cambiano stato; `403` su
  mismatch. Doppia difesa con `SameSite=Strict`.
- **Login:** throttling anti-guessing prima di qualunque verifica; `401` su credenziale
  errata.

Nessuna correzione necessaria. Osservazione minore (non vulnerabilità, non corretta): la
`POST /logout` non verifica il token CSRF, ma `SameSite=Strict` impedisce comunque il POST
cross-site; un «forced logout» è a basso impatto e il logout è spesso CSRF-exempt per
scelta. Nessun endpoint dati risulta privo di autenticazione.
