## FASE 3 — Correzione applicata: SEC-4.2 (valutare l'ultimo run, non «uno qualsiasi»)

**Difetto (fedeltà fail-closed).** `audit()` calcolava `successful` con
`any(run.conclusion == "success")` tra i run dello stesso check sullo SHA. GitHub, invece, valuta
un required-check in base al suo **run più recente**. Conseguenza: un check il cui ultimo run è
`failure` ma con un run precedente `success` veniva dichiarato **PASS** dall'audit post-merge,
mentre GitHub lo considera rosso — l'audit poteva certificare «tutto verde» uno SHA che GitHub
avrebbe bloccato.

**Correzione.** Nuovo helper `_latest_run(runs, source_id)` che restituisce il run più recente per
quel source (per `started_at`, tie-break `id`). `successful` e `terminal_failure` ora guardano solo
il run più recente per `(check, source)`. Un re-run fallito successivo prevale (→ non soddisfatto,
terminale); un re-run riuscito successivo soddisfa il check. **Nessun caso a run singolo cambia**
(i test preesistenti restano verdi), quindi è una correzione di fedeltà senza regressioni.

```python
# prima — "uno qualsiasi dei run è verde" (ottimistico, diverge da GitHub):
source_success = {sid: any(run.conclusion == "success" and <match source> for run in matching) ...}
# dopo — "il run più recente per source è verde" (come GitHub, fail-closed):
source_latest  = {sid: _latest_run(matching, sid) for sid in required_sources}
source_success = {sid: (run is not None and run.get("conclusion") == "success") ...}
```

**Verifica.** Ruff (`check` + `format`) ✅; `mypy src` (gate reale) ✅ (i 2 avvisi su
`scripts/audit_required_checks.py` — `yaml` senza stub e `_effective_rules` — sono **preesistenti**
e fuori dal gate `src`); Bandit ✅ (0 issue); pytest offline **verde** (riga finale, `PYTEST_RC=0`).
Regressioni in `tests/unit/test_required_checks_audit.py`: un re-run fallito successivo prevale su un
success precedente (→ fail + terminale); un re-run riuscito successivo soddisfa il check.

## FASE 7 — Correzione applicata: redazione segreti nelle evidenze Themis

**Difetto (anti-leak, fail-closed).** `themis/base._evidence` redige stdout/stderr degli
scanner prima di salvarli come `raw_evidence`. La regex `_SECRET_ASSIGNMENT` usava `\b` +
alternanza fissa di keyword e separatore `[:=]` nudo, divergendo dal predicato di sensibilità
dell'audit (`_sensitive_key`, substring su nome normalizzato). Conseguenza: tre classi di
segreto sopravvivevano nelle evidenze mentre `redact_mapping` le avrebbe redatte —
(1) JSON quotato `"api_key":"…"`/`"access_token":"…"` (virgolette+due punti rompono il
separatore); (2) nomi composti con termine sensibile non iniziale (`aws_secret_access_key`,
`refresh_token`, `client_secret`) — `\bsecret`/`\btoken` falliscono dopo `_`; (3) crumb
successivi di un header `Cookie` multi-valore.

**Correzione.** `_evidence` decide ora la sensibilità del *nome* con lo stesso predicato
dell'audit: `_sensitive_key` è promosso ad API pubblica `is_sensitive_key` (unica fonte di
verità, usata da `redact_mapping`, `redact_arguments` e dalle evidenze). La regex del nome è
ancorata a inizio-segmento con look-behind `(?<![\w.\-])`, tollera le virgolette JSON e
consuma ancora uno schema di auth opzionale nel valore (`Bearer <tok>`). Un callback
(`_redact_assignment`) redige il valore solo quando `is_sensitive_key(nome)` è vero.

**Linearità (ReDoS).** Il redattore scandisce l'intero output non fidato (fino a
`max_output_bytes`, milioni di byte) *prima* del troncamento: una bozza con prefisso
`[\w.-]*` + alternanza mostrava backtracking catastrofico (n=10k → hang). Il look-behind
ancora ogni nome a un solo start per segmento → O(n) (4.5 MB ≈ 280 ms). Guardia di
linearità aggiunta ai test.

**Verifica.** Ruff (`check`+`format`) ✅; `mypy src` ✅ (239 file); Bandit ✅ (0 issue);
pytest offline **verde** (2956 passed, 9 skipped), inclusi property-test di sicurezza e
mutation guardrail. Regressioni nuove in `tests/unit/test_themis_execution.py`
(JSON quotato, nomi composti, cookie multipli, guardia di linearità); nessuna over-redazione
dei campi non sensibili.

## FASE 8 — Correzione applicata: redazione audit strutturato (URL nel testo libero)

**Difetto (anti-leak, fail-closed).** `core/execution.redact_mapping` redige i record di audit
strutturati (`StructuredAuditRecord.metadata`, scritto da API/Web/jobs/CLI). Per i valori
stringa `_redact_value` usava `redact_url`, che riscrive **solo** una stringa che *è* un URL.
Un valore di metadata è però spesso una riga diagnostica di testo libero con un URL annidato
(es. `{"detail": "scanner fetched https://api/?api_key=SECRET during probe"}`): `redact_url`
lo lasciava invariato → segreto in chiaro nel record di audit. La stessa chiave sensibile
sarebbe stata redatta, ma un segreto in un URL dentro una frase sotto chiave non-sensibile
sfuggiva — lo stesso tipo di divergenza chiuso in FASE 7 sul lato evidenze.

**Correzione.** `_redact_value` usa ora `redact_text` per le stringhe: redige ogni URL trovato
nel testo ed è un superset di `redact_url` per una stringa che è già un URL (nessuna
sotto-redazione, i parametri non-segreto e il testo non-URL restano invariati). Il lato audit
è così allineato al redattore delle evidenze Themis.

**Verifica.** Ruff (`check`+`format`) ✅; `mypy src` ✅ (239 file); Bandit ✅; pytest offline
**verde** (3107 passed, 9 skipped). Regressione in `tests/unit/test_core_execution.py`
(URL-segreto annidato in testo libero sotto chiave non-sensibile; testo circostante e param
non-segreto preservati). Mutation gate verificato in locale: `x_redact_mapping` (8) e
`x__redact_value` (3) tutti uccisi.
