## English

### What Olympus does

Olympus is a single command, `olympus`, behind which live **9 modules** — 4 offensive (red), 3
defensive (blue), 2 for correlation/reporting — that would normally be 9 separate tools from 9
different projects, each with its own incompatible output format. Here they share the same
**data contract** (`core.Asset`, `core.Finding`, `core.Alert`, `core.Incident`): an asset
discovered by Argus can be verified by Helios, detected by Apollo, handled by Minerva, and end
up in the same report generated by Vulcan — keeping **the same ID** (`AST-2026-00001`) the
whole way through.

In short, here's the path data takes as it moves from one module to the next:

```
 domain / IP / URL / handle — always inside an authorized scope
        │
        ▼
  Argus · Helios · Artemis · Proteus     (🔴 red: discover and verify, never out of bounds)
        │  core.Asset + core.Finding (same ID)
        ▼
  Hermes · Apollo · Minerva              (🔵 blue: detect, correlate, keep custody of evidence)
        │  core.Alert + core.Incident
        ▼
       Vulcan                            (🟣 aggregates it all, dedupes, CVSS → pentest report)
```

You don't need to understand this diagram to start using Olympus — it's here only for the
curious, to explain why the modules share data. In practice you'll run individual
`olympus <module> <command>` commands, each explained one by one further down this guide.

This guide is written for someone who has never used Olympus before: it follows the order —
install, first run, the complete command list, an options legend, a full guided walkthrough on
a practice target included in the repo — so you can follow it start to finish without already
knowing anything.

### Requirements

- **Python 3.11 or newer**, with `pip`.
- An Internet connection **only** for the modules that do real lookups (Argus, Helios,

### Install and first run (step by step)

This section walks you, one step at a time, from nothing to a first real command run
successfully. No prior experience with Olympus is needed.

**Step 1 — Download and install.**

Open a terminal and paste:

First verify that Python 3.11 or newer is available (macOS commonly exposes it as `python3`,
not `python`):

```bash
python3 --version
```

If that command is missing on macOS, install Python from
[python.org](https://www.python.org/downloads/macos/) or with Homebrew (`brew install python`),
then open a new terminal. Do not use the legacy system Python.

```bash
git clone https://github.com/chiaraberti13/olympus-security.git
cd olympus-security
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

The `venv` is an isolated Python environment: everything you install stays inside the `.venv`
folder, without touching the rest of your system. Every time you reopen a terminal in this
folder, remember to reactivate it with `source .venv/bin/activate` (your terminal prompt shows
`(.venv)` when it's active).

**Step 2 — Verify the install.**

```bash
olympus --version
olympus --help
```

The first prints the installed version; the second lists the 9 available modules. If instead
you see `command not found: olympus`, the venv isn't active — repeat
`source .venv/bin/activate` inside the `olympus-security` folder.

**Step 3 — Your first real command (zero network, zero setup).**

Hermes, the secret scanner, makes no network requests and needs no scope file at all: it's the
fastest way to see Olympus do something real.

```bash
olympus hermes scan src --output /tmp/hermes-findings.json
```

Scans the source code for API keys, tokens and credentials accidentally left behind (known
regex patterns + entropy-based detection). This repository comes back clean (`0 potential
secret(s)`). The command **exits with code `1`** if it finds something (so you can chain it in
a CI pipeline), `0` if it finds nothing — that's expected behaviour, not an error.

**Step 4 — Understand scope, and run your first networked command.**

Offensive modules never accept a "free-hand" target: they require a **scope file**, a JSON
document explicitly listing what you're authorized to test. The repository ships one already
set up for a synthetic demo domain:

```bash
cat examples/input/argus-scope.json
```

```json
{
  "engagement": "olympus-demo-corp-2026",
  "allowed_domains": ["olympusdemocorp.example"]
}
```

Now try real passive DNS recon against that domain:

```bash
olympus argus scan --domain olympusdemocorp.example --scope examples/input/argus-scope.json
```

This really queries DNS, MX, SPF/DMARC, and exports the result to
`argus-assets.json` in the current directory as a `core.Asset` (pass `--output`
to write it elsewhere).

**Step 5 — See what happens outside scope.**

Now try a domain that is **not** listed in the scope file:

```bash
olympus argus scan --domain some-random-domain.com --scope examples/input/argus-scope.json
```

The command refuses to proceed, prints `blocked, out of scope`, and exits with code `3` — no
network request is ever made toward that domain. The event is written to the audit log
(`~/.local/state/olympus/audit/argus-blocked.log` by default — see **Where Olympus writes**):
this is how every offensive module respects its perimeter, always, with no silent exceptions.

**Step 6 — Aggregate everything into a report.**

Each module writes its own JSON output as a wrapper document (e.g. `{"assets": [...]}`); Vulcan
instead reads an **array** of `core.Asset`/`Finding`/`Alert` objects. Pull the array out with
one line of Python, then hand it to Vulcan:

```bash
python -c "import json; json.dump(json.load(open('argus-assets.json'))['assets'], \
  open('/tmp/vulcan-assets.json', 'w'))"

olympus vulcan report --engagement "olympus-demo-corp-2026" \
  --assets /tmp/vulcan-assets.json \
  --output vulcan-report.json \
  --markdown vulcan-report.md \
  --html vulcan-report.html
```

Vulcan merges, deduplicates and produces one consolidated report. Open `vulcan-report.html` in
a browser: it's a **self-contained** report (no external resources), ready to hand off.

From here you can explore the rest: the full command list below, or the **complete guided
walkthrough** further down this guide, which uses a real practice target (included in the
repo) to show the whole red→blue→report chain.

### Command list

Everything you can do goes through the `olympus` command. The table lists **every command** of
every module; for a single command's full details (every option, with defaults) always add
`--help`, e.g. `olympus argus scan --help`.

| Command | What it does |
|---|---|
| `olympus --version` | prints the installed version |
| `olympus core export-schemas <dir>` | exports the JSON Schema of every shared model (`Asset`, `Finding`, `Alert`, `Incident`…) |
| **Argus** — 🔴 OSINT & passive recon | |
| `olympus argus scan --domain <d>` | passive DNS/MX/SPF/DMARC recon on an authorized domain |
| `olympus argus fronting --domain <d>` | checks whether the domain sits behind a known CDN/WAF and whether a public subdomain leaks its origin IP |
| `olympus argus diff <a> <b>` | compares two Argus asset snapshots, no network |
| `olympus argus phone --number <n>` | profiles an in-scope number offline; opt-in authorized enrichment is returned explicitly in `enrichment` / `messaging` and never runs without `--i-am-authorized` |
| `olympus argus accounts --username <u>` | checks an in-scope handle through a validated HTTPS-only public-site registry; metadata requires explicit authorization |
| `olympus argus ip --ip <ip>` | profiles an in-scope IP offline; authorized optional geolocation uses the encrypted `ipwho.is` endpoint and is returned explicitly in `geo` |
| `olympus argus investigate --name <n>` | builds an authorized OSINT graph; every networked domain, IP, or username pivot is checked against its dedicated scope before lookup |
| **Helios** — 🔴 network attack-surface mapping | |
| `olympus helios scan <target>` | bounded, non-destructive TCP discovery; requires `--i-am-authorized` and CIDR scope before any connection |
| **Artemis** — 🔴 web recon | |
| `olympus artemis fetch --url <u>` | one bounded scope-safe GET; requires `--i-am-authorized` and prints metadata only |
| `olympus artemis fingerprint --url <u>` | identifies the technology stack from one authorized passive GET |
| `olympus artemis content --url <u>` | real, authorized and rate/deadline-bounded content discovery |
| `olympus artemis xss --url <u>` | authorized non-destructive reflected-XSS test (marker reflection only) |
| `olympus artemis metabase --url <u>` | authorized non-exploitative check for CVE-2026-72898 exposure |
| `olympus artemis check-scope --url <u>` | validates URL authorization without making any request |
| **Proteus** — 🔴 authorized phishing simulation | |
| `olympus proteus campaign --targets <f>` | requires confirmation; validates engagement, sender/recipient domains and HTTPS training origin, then writes owner-only versioned tokens |
| `olympus proteus page --engagement <e>` | renders the training page a clicker lands on (captures nothing) |
| `olympus proteus email --campaign <f> --token <t>` | renders the simulated lure email for one token |
| `olympus proteus report --campaign <f>` | summarizes campaign click-through (a training metric, never secrets) |
| **Hermes** — 🔵 secret & config scanner | |
| `olympus hermes scan <path>` | bounded regular-text/Git-history scan with stable baselines and masked SARIF; missing, symlink and partial inputs never report clean |
| **Apollo** — 🔵 detection engineering | |
| `olympus apollo test <rule> <event>` | evaluates one versioned exact-match rule against one normalized event with bounded input/deadline |
| `olympus apollo run --rules <dir> --events <f>` | streams versioned NDJSON through bounded rule/event/evaluation/alert limits; malformed records are reported as partial failure |
| `olympus apollo rules --rules <dir>` | loads, bounds and validates a non-empty rule directory with unique IDs |
| **Minerva** — 🔵 incident response & DFIR | |
| `olympus minerva triage <alerts> --title <t>` | creates a stable Incident from a strict bounded Apollo export |
| `olympus minerva record <evidence> <ledger> --actor <a> --action <act>` | locks, verifies and appends a private custody 2.0 entry anchored to the evidence SHA-256 |
| `olympus minerva verify <ledger>` | verifies hashes, digest identity, transitions and timestamps; missing chains fail |
| `olympus minerva timeline <ledger>` | prints a verified chronological timeline including evidence digests |
| **Vulcan** — 🟣 aggregation & reporting | |
| `olympus vulcan rank --findings <f>` | bounded strict loading, exact-ID deduplication and severity ranking |
| `olympus vulcan report --assets/--findings/--alerts <f>` | validates complete producer envelopes and renders one canonical report as atomic JSON plus optional safe Markdown/HTML |

### Legend of the main options

Many options repeat identically across commands. Instead of repeating them 30 times in the
table above, here they are explained once:

| Option | What it does | Where you'll find it |
|---|---|---|
| `--scope <path>` | JSON file listing what you're authorized to test (domains, CIDRs, URLs, numbers, handles…). Mandatory on every offensive module. | Argus, Helios, Artemis, Proteus |
| `--log <path>` | where to write the audit log of targets blocked for being out of scope | Argus, Helios, Artemis, Proteus |
| `--i-am-authorized` | explicit confirmation you have documented authorization for a real lookup or an active test (on top of scope) | Argus (enrichment), Artemis (active tests), Proteus |
| `--output <path>` | where to write the JSON export conforming to the `core` schema | almost every command |
| `--format table\|json` | renders output as a human-readable table, or as JSON for a pipe | `vulcan rank`, `minerva timeline`, `apollo rules` |
| `--asset-id <id>` | `core.Asset` id to attach the produced findings to, so they land on the same asset in Vulcan | Helios, Artemis, Argus fronting |
| `--concurrency <n>` | how many checks to run in parallel (bulk enumeration) | `argus accounts` |
| `--rate <sec>` | minimum seconds between requests, out of politeness toward the target | `argus accounts`, `artemis content` |
| `--jitter <ratio>` | fraction of `--rate` to randomize each wait by, so pacing is not a metronome | `artemis content` |
| `--deadline <sec>` | overall budget for the whole run, instead of per-request timeouts that add up | `artemis content`, `helios scan` |
| `--banner` | read (never send) the greeting of services that speak first, to identify them | `helios scan` |
| `--min-severity <lvl>` | only include findings from this severity up (`info`…`critical`) in the report | `vulcan report` |
| `--baseline` / `--write-baseline` | ignore already-accepted fingerprints / save the current ones as a baseline | `hermes scan` |

**Canonical exit codes** — the same across every module, so a CI pipeline can react to *why* a
command stopped, not just to the fact that it did:

| Code | Meaning |
|---|---|
| `0` | all good: full coverage, nothing to report |
| `1` | found something you may want to look at (a secret, a finding, an alert…) |
| `2` | usage or input error (bad flag, unreadable or malformed file) |
| `3` | **blocked**: the target is outside the authorized scope (and was logged) |
| `4` | **refused**: an explicit authorization flag (`--i-am-authorized`) was required and missing |
| `5` | **partial**: the run lost coverage, so its findings are not exhaustive |
| `6` | **failed**: nothing completed, so the result carries no information |
| `7` | **cancelled**: the run stopped on request before finishing |

Codes `5` and `6` are what let a pipeline tell "we looked everywhere and found
nothing" from "we could not look" — see [run status and coverage](run-status.md).

**Configuration file** (optional) — to stop repeating the same flags, create `olympus.toml` in
the folder you run commands from (or `~/.olympus.toml`, or point `$OLYMPUS_CONFIG` at a
path):

```toml
[http]
timeout = 15.0
retries = 3
rate = 0.25
backoff = 0.5
jitter = 0.2   # spread each retry wait by +/- this fraction (0 = off)
```

**Where Olympus writes** — two kinds of file, two different homes:

| Kind | Default | Override |
|---|---|---|
| **Reports and exports** — what you asked for (`--output`, `--markdown`, `--html`) | a plain filename in the directory you ran the command from, e.g. `argus-assets.json` | `--output <path>` |
| **Audit and block logs** — written implicitly when a target is refused (`--log`) | `~/.local/state/olympus/audit/`, following `$XDG_STATE_HOME` when set | `--log <path>`, or `$OLYMPUS_STATE_DIR` for all of them at once |

Audit logs deliberately do *not* depend on your working directory: they are written as a side
effect of a scope violation, so they must land in the same place whether you ran the command
from your home directory or from a checkout. `OLYMPUS_STATE_DIR` is read once at startup.

### Guided walkthrough: from recon to report, on a practice target included in the repo

The repository ships **Mars**, a deliberately vulnerable target that runs locally
(`127.0.0.1`, synthetic data only): the right way to practise the *real* tools against
something you're always authorized to test, without having to find an external domain.

```bash
# Start the target (in a separate terminal, leave it running)
python labs/mars/target/app.py        # http://127.0.0.1:8081

# In the other terminal, with the venv active:
S=labs/mars/target/practice-scope.json

olympus artemis fingerprint --url http://127.0.0.1:8081/ --scope $S
olympus artemis content --url http://127.0.0.1:8081/app \
  --wordlist examples/input/artemis-content-wordlist.txt --scope $S --i-am-authorized
olympus artemis xss --url "http://127.0.0.1:8081/app/search?q=x" --param q \
  --scope $S --i-am-authorized
olympus artemis metabase --url http://127.0.0.1:8081 --scope $S --i-am-authorized

# Then the blue side: detect a simulated post-exploitation chain (never a real capture)
olympus apollo run --rules examples/input/apollo-redteam \
  --events labs/mars/target/mars-post-exploitation.ndjson
```

The complete step-by-step guide, explaining every deliberate weakness of the target, is in
[`labs/mars/README.md`](../labs/mars/README.md).

### Troubleshooting

- **`command not found: olympus`** — the venv isn't active. Run
  `source .venv/bin/activate` inside the `olympus-security` folder.
- **`ModuleNotFoundError` or import errors** — the install didn't complete, or was run outside
  the venv. Repeat `pip install -e ".[dev]"` with the venv active.
- **`blocked, out of scope` (exit code `3`)** — expected behaviour, not a bug: the target isn't
  in the file passed via `--scope`. Add it to the scope JSON if you really are authorized to
  test it.
- **`refused: --i-am-authorized required` (exit code `4`)** — the command performs a real
  lookup against a third party or an active test: only re-run it with `--i-am-authorized` if
  you genuinely have documented authorization.
- **`make check` fails on the coverage gate** — the dev dependencies are missing: make sure you
  installed with `pip install -e ".[dev]"` (not just `pip install -e .`) and that the venv is
  active.
- **A command doing real lookups hangs or times out** — check your connection, and double-check
  the scope you passed actually includes the target: without network, the offline modules
  (Hermes, Apollo, Minerva) keep working normally.
- **Want to try Mars but don't have Docker** — you don't need it:
  `python labs/mars/target/app.py` starts the target without Docker, as shown above.

### Uninstalling

```bash
deactivate            # exit the venv, if active
rm -rf .venv           # removes the isolated Python environment and every installed dependency
cd .. && rm -rf olympus-security   # removes the repository itself, if you no longer need it
```

Nothing outside the project folder is touched: no file is written anywhere else on the system.

`.venv`, senza toccare il resto del sistema. Ogni volta che riapri un terminale in questa
cartella, ricordati di riattivarlo con `source .venv/bin/activate` (il prompt del terminale
mostrerà `(.venv)` quando è attivo).

**Passo 2 — Verifica l'installazione.**

```bash
olympus --version
olympus --help
```

Il primo stampa la versione installata; il secondo elenca i 9 moduli disponibili. Se invece
di questo vedi `command not found: olympus`, il venv non è attivo — ripeti
`source .venv/bin/activate` dentro la cartella `olympus-security`.

**Passo 3 — Il tuo primo comando reale (zero rete, zero configurazione).**

Hermes, lo scanner di secret, non fa nessuna richiesta di rete e non ha bisogno di alcun file
di scope: è il modo più veloce per vedere Olympus fare qualcosa di vero.

```bash
olympus hermes scan src --output /tmp/hermes-findings.json
```

Scansiona il codice sorgente alla ricerca di chiavi API, token e credenziali dimenticate
(regex note + rilevamento tramite entropia). Su questo repository esce pulito (`0 potential
secret(s)`). Il comando **esce con codice `1`** se trova qualcosa (così puoi incatenarlo in una
pipeline CI), `0` se non trova nulla — non è un errore, è il funzionamento previsto.

**Passo 4 — Capisci lo scope, ed esegui il tuo primo comando in rete.**

I moduli offensivi non accettano mai un target "a mano libera": vogliono un **file di scope**,
un JSON che elenca esplicitamente cosa sei autorizzato a testare. Il repository ne include uno
già pronto per un dominio di dimostrazione sintetico:

```bash
cat examples/input/argus-scope.json
```

```json
{
  "engagement": "olympus-demo-corp-2026",
  "allowed_domains": ["olympusdemocorp.example"]
}
```

Ora prova la ricognizione DNS passiva reale contro quel dominio:

```bash
olympus argus scan --domain olympusdemocorp.example --scope examples/input/argus-scope.json
```

Interroga davvero DNS, MX, SPF/DMARC ed esporta il risultato in
`argus-assets.json` nella directory corrente come `core.Asset` (usa `--output`
per scriverlo altrove).

**Passo 5 — Guarda cosa succede fuori dallo scope.**

Prova adesso un dominio **non** elencato nel file di scope:

```bash
olympus argus scan --domain un-dominio-a-caso.com --scope examples/input/argus-scope.json
```

Il comando si rifiuta di procedere, stampa `blocked, out of scope` ed esce con codice `3` —
niente richiesta di rete viene mai fatta verso quel dominio. L'evento resta scritto nel log di
audit (`~/.local/state/olympus/audit/argus-blocked.log` di default — vedi **Dove scrive
Olympus**): è così che ogni modulo offensivo rispetta il perimetro, sempre, senza eccezioni
silenziose.

**Passo 6 — Aggrega tutto in un report.**

Ogni modulo scrive il proprio output JSON come un documento avvolgente (es.
`{"assets": [...]}`); Vulcan invece legge un **array** di oggetti `core.Asset`/`Finding`/
`Alert`. Estrai l'array con una riga di Python, poi passalo a Vulcan:

```bash
python -c "import json; json.dump(json.load(open('argus-assets.json'))['assets'], \
  open('/tmp/vulcan-assets.json', 'w'))"

olympus vulcan report --engagement "olympus-demo-corp-2026" \
  --assets /tmp/vulcan-assets.json \
  --output vulcan-report.json \
  --markdown vulcan-report.md \
  --html vulcan-report.html
```

Vulcan unisce, deduplica e produce un report unico. Apri `vulcan-report.html` in un browser: è
un report **autosufficiente** (nessuna risorsa esterna), pronto da consegnare.

Da qui puoi esplorare il resto: l'elenco completo dei comandi qui sotto, oppure il **percorso
guidato completo** più avanti in questa guida, che usa un bersaglio di prova reale (incluso nel
repository) per mostrare l'intera catena red→blue→report.

### Elenco dei comandi

Tutto quello che puoi fare passa dal comando `olympus`. La tabella elenca **ogni comando** di
ogni modulo; per i dettagli di un singolo comando (tutte le opzioni, con i default) aggiungi
sempre `--help`, es. `olympus argus scan --help`.

| Comando | Cosa fa |
|---|---|
| `olympus --version` | stampa la versione installata |
| `olympus core export-schemas <dir>` | esporta i JSON Schema di tutti i modelli condivisi (`Asset`, `Finding`, `Alert`, `Incident`…) |
| **Argus** — 🔴 OSINT & recon passiva | |
| `olympus argus scan --domain <d>` | ricognizione passiva DNS/MX/SPF/DMARC su un dominio autorizzato |
| `olympus argus fronting --domain <d>` | verifica se il dominio è dietro un CDN/WAF noto e se un sottodominio pubblico ne espone l'IP d'origine |
| `olympus argus diff <a> <b>` | confronta due snapshot di asset Argus, senza rete |
| `olympus argus phone --number <n>` | profila offline un numero in scope; gli arricchimenti autorizzati opzionali sono restituiti esplicitamente in `enrichment` / `messaging` e non partono senza `--i-am-authorized` |
| `olympus argus accounts --username <u>` | verifica un handle in scope tramite un registro validato di siti pubblici solo HTTPS; i metadati richiedono autorizzazione esplicita |
| `olympus argus ip --ip <ip>` | profila offline un IP in scope; la geolocalizzazione opzionale autorizzata usa l'endpoint cifrato `ipwho.is` ed è restituita esplicitamente in `geo` |
| `olympus argus investigate --name <n>` | costruisce un grafo OSINT autorizzato; ogni pivot di rete su dominio, IP o username viene verificato nel relativo scope prima del lookup |
| **Helios** — 🔴 mappatura della superficie di rete | |
| `olympus helios scan <target>` | discovery TCP non distruttiva e limitata; richiede `--i-am-authorized` e scope CIDR prima di ogni connessione |
| **Artemis** — 🔴 web recon | |
| `olympus artemis fetch --url <u>` | una GET scope-safe e limitata; richiede `--i-am-authorized` e stampa solo i metadati |
| `olympus artemis fingerprint --url <u>` | identifica lo stack da una GET passiva autorizzata |
| `olympus artemis content --url <u>` | content discovery reale, autorizzata e limitata da rate/deadline |
| `olympus artemis xss --url <u>` | test autorizzato non distruttivo di reflected XSS (solo marker) |
| `olympus artemis metabase --url <u>` | verifica autorizzata e non distruttiva dell'esposizione a CVE-2026-72898 |
| `olympus artemis check-scope --url <u>` | valida l'autorizzazione dell'URL senza fare alcuna richiesta |
| **Proteus** — 🔴 simulazione phishing autorizzata | |
| `olympus proteus campaign --targets <f>` | richiede conferma; valida ingaggio, domini mittente/destinatari e origine HTTPS di training, poi salva token versionati con permessi solo proprietario |
| `olympus proteus page --engagement <e>` | genera la pagina di training che vede chi clicca (non cattura nulla) |
| `olympus proteus email --campaign <f> --token <t>` | genera l'email-esca simulata per un token |
| `olympus proteus report --campaign <f>` | riassume il click-through della campagna (metrica di training, mai segreti) |
| **Hermes** — 🔵 secret & config scanner | |
| `olympus hermes scan <path>` | scansione limitata di testo regolare/history Git con baseline stabili e SARIF mascherato; input mancanti, symlink o parziali non risultano puliti |
| **Apollo** — 🔵 detection engineering | |
| `olympus apollo test <rule> <event>` | valuta una regola versionata a confronto esatto contro un evento normalizzato, con input/deadline limitati |
| `olympus apollo run --rules <dir> --events <f>` | elabora NDJSON versionato con limiti su regole/eventi/valutazioni/alert; i record malformati causano un fallimento parziale esplicito |
| `olympus apollo rules --rules <dir>` | carica, limita e valida una cartella non vuota con ID di regola univoci |
| **Minerva** — 🔵 incident response & DFIR | |
| `olympus minerva triage <alerts> --title <t>` | crea un Incident stabile da un export Apollo rigoroso e limitato |
| `olympus minerva record <evidence> <ledger> --actor <a> --action <act>` | blocca, verifica e aggiunge una voce privata custody 2.0 ancorata allo SHA-256 del reperto |
| `olympus minerva verify <ledger>` | verifica hash, identità del digest, transizioni e timestamp; una catena mancante fallisce |
| `olympus minerva timeline <ledger>` | stampa una timeline verificata che include i digest dei reperti |
| **Vulcan** — 🟣 aggregazione & report | |
| `olympus vulcan rank --findings <f>` | caricamento rigoroso e limitato, deduplicazione per ID esatto e ranking per severità |
| `olympus vulcan report --assets/--findings/--alerts <f>` | valida gli envelope completi e genera un report canonico come JSON atomico più Markdown/HTML sicuri opzionali |

### Legenda delle opzioni principali

Molte opzioni si ripetono identiche su più comandi. Invece di ripeterle 30 volte nella tabella
sopra, eccole spiegate una volta sola:

| Opzione | Cosa fa | Dove la trovi |
|---|---|---|
| `--scope <path>` | file JSON con l'elenco di ciò che sei autorizzato a testare (domini, CIDR, URL, numeri, handle…). Obbligatorio su ogni modulo offensivo. | Argus, Helios, Artemis, Proteus |
| `--log <path>` | dove scrivere il log di audit dei target bloccati perché fuori scope | Argus, Helios, Artemis, Proteus |
| `--i-am-authorized` | conferma esplicita che hai l'autorizzazione documentata per un lookup reale o un test attivo (oltre allo scope) | Argus (arricchimenti), Artemis (test attivi), Proteus |
| `--output <path>` | dove scrivere l'export JSON conforme allo schema `core` | quasi tutti i comandi |
| `--format table\|json` | rende l'output leggibile a schermo (tabella) oppure in JSON per una pipe | `vulcan rank`, `minerva timeline`, `apollo rules` |
| `--asset-id <id>` | ID `core.Asset` a cui agganciare i finding prodotti, per farli confluire sullo stesso asset in Vulcan | Helios, Artemis, Argus fronting |
| `--concurrency <n>` | quante verifiche in parallelo (enumerazioni di massa) | `argus accounts` |
| `--rate <sec>` | secondi minimi tra una richiesta e l'altra, per cortesia verso il target | `argus accounts`, `artemis content` |
| `--min-severity <liv>` | include nel report solo i finding a partire da questa severità (`info`…`critical`) | `vulcan report` |
| `--baseline` / `--write-baseline` | ignora fingerprint già accettati / salva quelli attuali come baseline | `hermes scan` |

**Exit code canonici** — uguali su tutti i moduli, così una pipeline CI può reagire al *perché*
un comando si è fermato, non solo al fatto che si sia fermato:

| Codice | Significato |
|---|---|
| `0` | tutto ok: copertura completa, niente da segnalare |
| `1` | trovato qualcosa che potresti voler guardare (secret, finding, alert…) |
| `2` | errore d'uso o d'input (flag sbagliato, file illeggibile o malformato) |
| `3` | **bloccato**: il target è fuori dallo scope autorizzato (ed è stato loggato) |
| `4` | **rifiutato**: serviva un flag di autorizzazione esplicito (`--i-am-authorized`) e non c'era |
| `5` | **parziale**: l'esecuzione ha perso copertura, quindi i finding non sono esaustivi |
| `6` | **fallito**: nulla è stato completato, il risultato non porta informazione |
| `7` | **annullato**: l'esecuzione si è fermata su richiesta prima di finire |

I codici `5` e `6` sono ciò che permette di distinguere "abbiamo guardato ovunque e non
c'era niente" da "non siamo riusciti a guardare" — vedi
[stato e copertura](run-status.md).

**File di configurazione** (opzionale) — per non ripetere sempre gli stessi flag, crea
`olympus.toml` nella cartella da cui lanci i comandi (oppure `~/.olympus.toml`, oppure indica
un percorso con `$OLYMPUS_CONFIG`):

```toml
[http]
timeout = 15.0
retries = 3
rate = 0.25
backoff = 0.5
jitter = 0.2   # distribuisce ogni attesa di retry di +/- questa frazione (0 = off)
```

**Dove scrive Olympus** — due tipi di file, due destinazioni diverse:

| Tipo | Default | Override |
|---|---|---|
| **Report ed export** — quello che hai chiesto (`--output`, `--markdown`, `--html`) | un nome di file semplice nella directory da cui hai lanciato il comando, es. `argus-assets.json` | `--output <path>` |
| **Log di audit e di blocco** — scritti implicitamente quando un bersaglio viene rifiutato (`--log`) | `~/.local/state/olympus/audit/`, rispettando `$XDG_STATE_HOME` se impostata | `--log <path>`, oppure `$OLYMPUS_STATE_DIR` per tutti insieme |

I log di audit di proposito *non* dipendono dalla directory di lavoro: sono scritti come
effetto collaterale di una violazione di scope, quindi devono finire sempre nello stesso posto,
che tu abbia lanciato il comando dalla home o da un checkout. `OLYMPUS_STATE_DIR` viene letta
una volta sola all'avvio.

### Percorso guidato: dal recon al report, su un bersaglio di prova incluso

Il repository include **Mars**, un bersaglio volutamente vulnerabile che gira in locale
(`127.0.0.1`, solo dati sintetici): è il modo giusto per esercitarsi con i tool *reali* contro
qualcosa che sei sempre autorizzato a testare, senza dover cercare un dominio esterno.

```bash
# Avvia il bersaglio (in un terminale separato, lo lasci aperto)
python labs/mars/target/app.py        # http://127.0.0.1:8081

# Nell'altro terminale, con il venv attivo:
S=labs/mars/target/practice-scope.json

olympus artemis fingerprint --url http://127.0.0.1:8081/ --scope $S
olympus artemis content --url http://127.0.0.1:8081/app \
  --wordlist examples/input/artemis-content-wordlist.txt --scope $S --i-am-authorized
olympus artemis xss --url "http://127.0.0.1:8081/app/search?q=x" --param q \
  --scope $S --i-am-authorized
olympus artemis metabase --url http://127.0.0.1:8081 --scope $S --i-am-authorized

# Poi il lato blue: rileva un post-exploitation simulato (mai una cattura reale)
olympus apollo run --rules examples/input/apollo-redteam \
  --events labs/mars/target/mars-post-exploitation.ndjson
```

La guida completa, passo passo, con spiegazione di ogni debolezza del bersaglio, è in
[`labs/mars/README.md`](../labs/mars/README.md).

### Se qualcosa non va

- **`command not found: olympus`** — il venv non è attivo. `source .venv/bin/activate` dentro
  la cartella `olympus-security`.
- **`ModuleNotFoundError` o errori d'import** — l'installazione non è andata a buon fine o è
  stata fatta fuori dal venv. Ripeti `pip install -e ".[dev]"` col venv attivo.
- **`blocked, out of scope` (uscita `3`)** — comportamento previsto, non un bug: il target non
  è nel file passato con `--scope`. Aggiungilo al JSON di scope se sei davvero autorizzato a
  testarlo.
- **`refused: --i-am-authorized required` (uscita `4`)** — il comando fa un lookup reale verso
  terzi o un test attivo: rilancialo con `--i-am-authorized` solo se hai davvero
  l'autorizzazione documentata.
- **`make check` fallisce sulla coverage** — mancano le dipendenze di sviluppo: assicurati di
  aver installato con `pip install -e ".[dev]"` (non solo `pip install -e .`) e di avere il
  venv attivo.
- **Un comando che fa lookup reali non risponde/va in timeout** — verifica la connessione, e
  ricontrolla di aver passato uno scope che include davvero il target: senza rete i moduli
  offline (Hermes, Apollo, Minerva) continuano comunque a funzionare normalmente.
- **Vuoi provare Mars ma non hai Docker** — non serve: `python labs/mars/target/app.py` avvia
  il bersaglio senza Docker, come mostrato sopra.

### Disinstallazione

```bash
deactivate            # esci dal venv, se attivo
rm -rf .venv           # rimuove l'ambiente Python isolato e tutte le dipendenze installate
cd .. && rm -rf olympus-security   # rimuove il repository stesso, se non ti serve più
```

Non tocca nulla fuori dalla cartella del progetto: nessun file scritto altrove sul sistema.
