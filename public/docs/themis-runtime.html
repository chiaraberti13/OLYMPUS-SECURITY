Native Themis runtime — SEC-A

Italiano

olympus themis api, serve/web, migrate e workers eseguono il control plane nativo dalla wheel installata. API e Web riusano autenticazione, scope registrati, audit redatto e lo stesso archivio job; i worker eseguono soltanto la richiesta tipizzata attraverso il servizio applicativo Themis.

Limite di deployment

Eseguire una sola istanza e un solo processo per ciascun servizio API/Web. Il rate limit API/Web usa un RateLimiter in-process; i cookie Web sono firmati con un segreto casuale del processo, quindi un riavvio invalida le sessioni esistenti e più worker Web non condividono la verifica delle sessioni. Lo store SQLite coordina le claim dei job tra processi, ma ciò non rende distribuiti identità, rate limit o sessioni browser. Non dichiariamo affidabile il deployment Web orizzontale/multiworker finché questi stati non hanno backend condivisi e test di carico. Worker scanner separati possono condividere lo stesso database job entro il limite di concorrenza configurato.

I benchmark sintetici locali della coda sono solo diagnostici: non stabiliscono SLO API/Web o capacità production. Vedi performance.md e DEV-E-02 nella roadmap.

pip install "olympus-security[themis]"
olympus themis migrate --database .olympus/themis-jobs.sqlite3
olympus themis api --scope-directory .olympus/scopes
olympus themis serve --scope-directory .olympus/scopes \
  --ssl-certfile cert.pem --ssl-keyfile key.pem
olympus themis workers --database .olympus/themis-jobs.sqlite3
olympus themis workers --once --database .olympus/themis-jobs.sqlite3

Per i job API/Web protetti da manifest firmato, API, Web e worker devono condividere l'archivio revoche e la chiave pubblica dell'approvatore:

olympus themis workers --database .olympus/themis-jobs.sqlite3 \
  --engagement-storage .olympus/engagements \
  --manifest-public-key approver-ed25519-public.pem

Avviare anche il Web con --engagement-storage .olympus/engagements --manifest-public-key approver-ed25519-public.pem: il wizard richiede il JSON firmato, lo verifica in anteprima e di nuovo al submit, quindi lega il digest al job. Senza la chiave fissata la modalità compatibile può ancora accodare lavoro offline, ma un worker live rifiuta ogni job privo di manifest legato prima dell'applicazione scanner.

L'esecuzione diretta non è una scorciatoia: quando THEMIS_ENABLE_LIVE_SCANS=true, olympus themis run richiede sempre --signed-manifest, --manifest-public-key e --engagement-storage. Verifica firma, digest, revoca, finestra, target e scanner prima del servizio applicativo, conserva il documento per controlli successivi e assegna un job ID effimero al risultato. Autorizzazioni accettate e rifiutate sono registrate nell'audit senza copiarvi il manifest. La simulazione resta offline e non richiede un manifest.

L'API conserva il documento firmato verificato, non solo il digest. Prima di avviare lo scanner il worker ricarica quel documento e ricontrolla firma, digest, revoca, finestra, target e tecnica. Un digest senza documento o un worker privo del verificatore viene classificato policy_denied, senza traffico.

Prima di avviare API/Web, creare la directory degli scope e configurare OLYMPUS_THEMIS_API_KEY (almeno 32 caratteri casuali) oppure --identities con un registro di identità. La chiave condivisa concede per default solo capabilities:read; altri permessi si configurano esplicitamente con --api-key-scopes (preferire identità nominate con privilegi minimi). Il flag --i-am-authorized e il controllo di scope restano necessari per ogni job. THEMIS_ENABLE_LIVE_SCANS resta false per default: una scansione disabilitata o un binario assente produce partial, senza finding inventati. La Web UI usa cookie Secure: usare HTTPS anche per la sessione browser locale. I bind non-loopback richiedono certificato e chiave.

L'API è fail-closed verso le origini browser (ROADMAP API-4): per default non emette alcun header Access-Control-Allow-Origin, quindi nessun sito cross-origin può leggere una risposta. Per un deployment separato (frontend su dominio proprio) elencare ogni origine esatta con il flag ripetibile --cors-allow-origin https://app.example.com (schema http/https, host e porta opzionale; niente path, query, fragment, userinfo o slash finale). Il wildcard * è rifiutato all'avvio e l'origine non è mai riflessa: le credenziali sono ammesse solo contro questa allowlist esplicita, con metodi (GET, POST) e header consentiti ristretti.

Il worker continuo stampa una riga JSON quando è pronto e una per ogni job terminato. Una singola scansione fallita/parziale non interrompe il servizio. Ogni processo esegue un job alla volta; processi distinti condividono i claim atomici e i lease SQLite. Prima di ogni claim la stessa transazione conta i job running: --max-concurrent-jobs (default 1, intervallo 1–4096) impone così un limite aggregato fra tutti i worker sul medesimo database. Le repliche devono usare lo stesso valore; lease scaduti sono recuperati prima del conteggio e non bloccano capacità. --poll-interval è limitato a 0,05–30 secondi. API e Web limitano per default a 64 le richieste concorrenti complessive tra i processi che condividono lo stesso --database; il limite si può regolare con --max-concurrent-requests (1–4096). Un sidecar SQLite <database>.requests usa acquisizioni atomiche e lease rinnovabili: recupera capacità dopo un crash, rifiuta con 503 e Retry-After: 1 invece di accodare e non contiene payload o identità. Tutte le repliche devono condividere lo stesso file e lo stesso limite; deployment multi-host senza volume condiviso richiedono ancora un limite trusted a monte. Il sidecar deve essere incluso nel backup solo per diagnostica, non per il ripristino: le lease scadute vengono eliminate automaticamente. SIGINT/SIGTERM interrompono anche l'attesa a coda vuota, propagano la cancellazione allo scanner attivo e impediscono nuovi claim. Il servizio termina con codice 7; --once restituisce il codice canonico del job (0 coda vuota/nessun finding, 1 finding, 4 policy negata, 5 parziale, 6 fallito/timeout, 7 cancellato).

Decisione sulla coda dei job

Per il deployment attuale manteniamo la coda persistente SQLite e i worker Themis su un host container, fuori da Vercel. API, Web e worker condividono lo stesso volume locale. Il claim atomico, le lease rinnovabili e il limite aggregato coprono il coordinamento richiesto su questo host.

OpzioneQuando serveCosto operativo
SQLite e worker ThemisUn host con volume locale e capacità verificataUn solo archivio per stato e coda, con scritture serializzate
Postgres e worker ThemisWorker su più host o contesa di scrittura misurabileMigrazione dello store e verifica transazionale dei claim e delle lease
Broker dedicatoNecessità dimostrata di accodamento indipendente dallo store o di routing tra più codeServizio aggiuntivo e coordinamento tra messaggi e stato dei job

Riaprire la decisione se serve distribuire i worker su più host, oppure se sotto il carico previsto il tempo di attesa dei job supera l'obiettivo operativo o i log mostrano contesa SQLite persistente. Prima di cambiare architettura, registrare profondità della coda, tempo da enqueue a claim, errori di lock e recupero delle lease. Valutare Postgres con DATA-2 per il coordinamento multi-host. Se occorre un broker, usare l'identità del job per deduplicare le consegne e verificare perdita del worker, retry e coerenza dello stato in API-3 prima dell'adozione.

I test di claim, concorrenza e recupero delle lease sono in tests/unit/test_themis_jobs.py.

Migrazione e rollback

migrate crea o aggiorna il database nativo dei job, con DDL e versione in un'unica transazione. Le migrazioni native già supportate conservano job, idempotenza e stati; eseguirlo nuovamente è sicuro. Un database VAP/estraneo, una versione futura o non supportata e un symlink sono rifiutati. Non puntare il comando a vap.db: la conversione dei dati legacy richiede la successiva matrice completa di parità SEC-A.

Fermare API/Web/worker prima del backup. Usare il backup SQLite (che include il contenuto WAL) o copiare DB/WAL dopo la chiusura di tutte le connessioni. Per il rollback fermare i servizi, ripristinare il backup nativo insieme alla versione Olympus corrispondente e riavviare. Conservare il volume VAP precedente separatamente; il nuovo stack usa themis-data. Evitare docker compose down -v se si desidera conservare evidenze e job.

Prima di progettare una conversione, creare uno snapshot read-only del database VAP archiviato:

olympus themis legacy-snapshot --source vap.db \
  --backup migration/vap.backup.sqlite3 \
  --output migration/vap.snapshot.json

Il comando non modifica vap.db, non crea job nativi e non accetta symlink o destinazioni già esistenti. Il backup SQLite consistente e il manifest sono owner-only. Il contratto olympus.legacy-vap-snapshot 1.0.0 registra digest, conteggi, chiavi di migrazione deterministiche e decisioni sugli stati. Le righe queued/running sono blocked_active, mentre stati sconosciuti o ambigui restano unmapped: nessuna scansione viene riattivata senza nuova autorizzazione. Target e query secret sono esclusi dal manifest: resta soltanto il digest del target, mentre il valore originale rimane nel backup. Consent, audit e analytics sono conteggiati ma esclusi dal manifest perché richiedono valutazioni separate di finalità, privacy e provenienza.

Prima di usare lo snapshot come input per una futura conversione, verificare insieme tutti e tre gli artefatti:

olympus themis legacy-verify --source vap.db \
  --backup migration/vap.backup.sqlite3 \
  --manifest migration/vap.snapshot.json

La verifica è in sola lettura e fallisce se sorgente, backup o manifest sono cambiati, se il contratto non è esattamente la versione supportata, se PRAGMA integrity_check fallisce o se l'inventario ricostruito dal backup non coincide. Un esito positivo non autorizza né importa scansioni.

Generare quindi il piano revisionabile, ancora non eseguibile:

olympus themis legacy-plan --source vap.db \
  --backup migration/vap.backup.sqlite3 \
  --manifest migration/vap.snapshot.json \
  --output migration/vap.conversion-plan.json

Il contratto olympus.legacy-vap-conversion-plan 1.0.0 collega il piano ai digest del manifest e del backup e classifica ogni record come terminale da revisionare oppure da trattenere perché attivo, eliminato, con stato ambiguo o senza adapter nativo. Non contiene target in chiaro, non eredita autorizzazioni legacy e dichiara esplicitamente zero job eseguibili creati. Il file è create-only e owner-only; la futura importazione richiederà un comando separato, un engagement manifest corrente e un'ulteriore revisione SEC-A.

Approvare quindi soltanto le chiavi revisionate usando un manifest di engagement corrente e la chiave pubblica dell'approvatore:

olympus themis legacy-approve --source vap.db \
  --backup migration/vap.backup.sqlite3 \
  --manifest migration/vap.snapshot.json \
  --plan migration/vap.conversion-plan.json \
  --signed-manifest engagement.signed.json \
  --manifest-public-key approver.pub.pem \
  --migration-key <sha256> \
  --output migration/vap.import-approval.json

Il contratto olympus.legacy-vap-import-approval 1.0.0 verifica nuovamente snapshot e piano, firma Ed25519, revoche opzionali, finestra temporale, tecnica, scope e limite dei target. Accetta solo record review_terminal selezionati esplicitamente. Il receipt contiene digest e chiavi di migrazione, mai target in chiaro; non considera autorizzata retroattivamente l'esecuzione storica e crea zero job.

Importare infine soltanto le righe approvate come record terminali nativi:

olympus themis legacy-import --source vap.db \
  --backup migration/vap.backup.sqlite3 \
  --manifest migration/vap.snapshot.json \
  --plan migration/vap.conversion-plan.json \
  --approval migration/vap.import-approval.json \
  --signed-manifest engagement.signed.json \
  --manifest-public-key approver.pub.pem \
  --database .olympus/themis-jobs.sqlite3 \
  --output migration/vap.import-receipt.json

legacy-import rivalida l'intera catena, la firma, le revoche e lo scope al momento dell'import. Scrive in una singola transazione record idempotenti già terminali e con authorized=false: nessun worker può reclamarli. Un legacy completed diventa partial, mai succeeded, perché findings e configurazione non affidabili restano nel backup e nel job sono conservati solo i digest; failed e canceled restano distinti. I parametri query sensibili del target sono redatti prima della persistenza. Il receipt create-only olympus.legacy-vap-import-receipt 1.0.0 contiene solo provenienza minimizzata, ribadisce che l'esecuzione storica non è autorizzata retroattivamente e dichiara zero job eseguibili.

Docker

L'immagine docker/Dockerfile installa la wheel, include template/statici e non copia vendor/. Il Compose avvia migrazione, API HTTPS, Web HTTPS e worker SQLite senza broker. L'overlay scanner cambia soltanto l'immagine del worker.

Preparare prima dello startup:

  1. .olympus/scopes/ con i documenti di scope autorizzati;
  2. .olympus/config/themis-api-identities.json con identità a minimo privilegio,

generate da olympus themis identities init/add --file …;

  1. .olympus/tls/cert.pem e .olympus/tls/key.pem, con certificato valido per

l'hostname usato dal browser e chiave privata protetta.

Queste directory sono bind mount in sola lettura. File e directory devono essere leggibili/attraversabili dall'UID/GID 10001:10001 del container; il registro e la chiave restano owner-only (0600). Il worker riceve scope e volume dati, senza registro credenziali o chiave TLS. L'immagine prepara il volume dati con il proprietario corretto; per un volume già esistente verificare la proprietà prima del riuso.

docker compose up --build
# API: https://localhost:8443 ; Web: https://localhost:8600
docker compose -f docker-compose.yml -f docker-compose.scanners.yml up --build
docker compose down

La configurazione fallisce all'avvio se mancano credenziali, scope o TLS. Servizi non-root, filesystem root read-only, capability rimosse, no-new-privileges, tmpfs e limiti memoria/PID sono espliciti. Il worker carica inoltre il profilo seccomp default-deny versionato in deploy/security/themis-scanner-seccomp.json; la migrazione non ha rete. Egress allowlist resta in SEC-B. API e Web sono collegati soltanto alla rete Compose interna control; worker e motori opzionali soltanto a scan-egress. Nessun servizio è dual-homed e i job attraversano il confine tramite il volume SQLite, non tramite una rotta di rete. scan-egress non è ancora limitata agli IP e alle porte dello scope validato. Sugli host AppArmor compatibili il profilo versionato deploy/security/olympus-themis-scanner.apparmor si installa fail-closed con sudo python scripts/manage_scanner_apparmor.py install e si applica con l'overlay docker-compose.apparmor.yml. L'overlay resta esplicito perché l'installazione del package non deve elevare privilegi. Le esecuzioni live verificano nel servizio applicativo il marker OCI e l'attestazione immagine a digest fissato insieme a rootfs read-only, capability zero, no-new-privileges e seccomp attivo. Un comando CLI host non può aggirare il gate con flag o variabili; simulazione e live disabilitato restano portabili. Il test container prova l'attestazione runtime, il rifiuto di una syscall e la terminazione entro un limite di un processo che ignora SIGTERM, richiedendo segnalazione del process group, escalation SIGKILL e report strutturato. Non dichiara isolamento scanner completo. Il profilo opzionale ZAP mantiene la sua chiave API obbligatoria; Compose richiede THEMIS_ZAP_API_KEY durante l'interpolazione anche quando quel profilo non viene avviato.

Usa un checkout allo SHA da distribuire e registra docker version e docker compose version. Prepara scope, identità e TLS come descritto sopra. Per il backend nativo con scanner live disattivati, dalla radice del checkout esegui:

export THEMIS_ENABLE_LIVE_SCANS=false
# Solo per questa sessione e con il profilo ZAP inattivo. Compose interpola
# comunque la variabile del servizio opzionale.
export THEMIS_ZAP_API_KEY=unused-native-compose-placeholder
docker compose config --quiet
docker compose up --build -d themis-api themis-app themis-worker
docker compose ps --all
curl --fail --cacert /percorso/ca.pem https://localhost:8443/health

Sostituisci il percorso della CA e usa il nome coperto dal certificato e la porta configurata. Verifica che la migrazione sia terminata con codice 0, che API, Web e worker siano in esecuzione e che GET /api/v1/jobs senza credenziali restituisca HTTP 401. Per fermare il backend usa docker compose down mantenendo il volume dati. Se abiliti ZAP, configura una chiave reale prima di avviarlo.

English

Deployment boundary

Run one instance and one process for each API/Web service. API and Web rate limits use an in-process RateLimiter; Web session cookies are signed with a random process-local secret, so a restart invalidates existing sessions and multiple Web workers do not share session verification state. The SQLite job store does coordinate job claims across processes, but that does not make the identity, rate-limit or browser-session state distributed. Horizontal/multiworker Web deployment is not a supported reliability claim until those states have shared backends and are load-tested. Separate scanner workers may share the same job database under its configured concurrency cap.

The local synthetic queue benchmarks are diagnostic only; they do not establish an API/Web SLO or production capacity. See performance.md and DEV-E-02 in the roadmap.

The installed wheel owns themis api, serve/web, migrate and workers. API and Web share the native authenticated, scoped and audited job store. Workers execute typed requests through the canonical application service, with live scans disabled by default and explicit partial coverage for missing or disabled engines. serve and web are the same command implementation. Use HTTPS for browser sessions (Secure cookies); non-loopback binds require a certificate and private key. Set a random 32+ character API credential or provide an identity register. A shared key defaults to capabilities:read; grant additional permissions explicitly with --api-key-scopes (prefer named, least-privilege identities). Scopes and per-job authorization stay mandatory. The API is fail-closed toward browser origins (ROADMAP API-4): by default it emits no Access-Control-Allow-Origin header, so no cross-origin site can read a response. For a split deployment (frontend on its own domain) list each exact origin with the repeatable flag --cors-allow-origin https://app.example.com (http/https scheme, host and optional port; no path, query, fragment, userinfo or trailing slash). The wildcard * is rejected at startup and the origin is never reflected: credentials are allowed only against this explicit allowlist, with restricted allowed methods (GET, POST) and headers. API and Web default to 64 aggregate concurrent requests across processes that share the same --database; tune this with --max-concurrent-requests (1–4096). A <database>.requests SQLite sidecar uses atomic acquisitions and renewable leases, recovers capacity after crashes, and contains no request payloads or identities. Excess requests receive 503 with Retry-After: 1 instead of entering an unbounded queue. Every replica must share that file and the same limit; multi-host deployments without a shared volume still need a trusted upstream limit. The sidecar is diagnostic backup material only, not restore state: expired leases are purged automatically.

The continuous worker emits NDJSON readiness/completion records, runs one job at a time and continues after individual job failures. Separate processes share atomic SQLite claims/leases and one aggregate running cap, configured consistently with --max-concurrent-jobs (default 1, range 1–4096). Expired leases are recovered before capacity is counted. Bounded polling is interruptible; SIGINT/SIGTERM cancel active execution and stop new claims, returning 7. --once processes at most one job and preserves canonical exit codes: 0 empty/clean, 1 findings, 4 denied, 5 partial, 6 failed/timed out, 7 cancelled.

For API/Web jobs protected by signed manifests, start workers with the same --engagement-storage and pinned --manifest-public-key used by the API and Web. The submitting service retains the verified signed document alongside the revocation register. The Web wizard verifies it at preview and again at launch; without a pinned Web key, its compatibility confirmation mode may queue offline work, but a live worker refuses every job without a bound manifest before the scanner application. Immediately before scanner execution, the worker reloads it and rechecks the signature, digest, revocation status, time window, target and technique. A bound digest without its document or without a configured verifier becomes policy_denied and produces no scanner traffic. With --audit, the worker records that decision as themis.manifest-authorization (authorized or refused) with the job ID, manifest digest and scanner; successful execution then carries the same job ID and digest in themis.native-scan and in the persisted olympus.themis-result 1.2.0 evidence document. URL query secrets remain redacted and the signed document is never copied into audit or results.

Migrations are idempotent and transactional for supported native job databases. Foreign/VAP files, unsupported/future versions and symlinks are refused; legacy data conversion is a separate SEC-A parity task. Stop services before backing up, use SQLite backup or copy DB/WAL after all connections close, and restore the native backup with its matching Olympus version for rollback. Keep the old VAP volume separate; the native stack uses themis-data.

Before any reviewed conversion, run olympus themis legacy-snapshot --source vap.db --backup migration/vap.backup.sqlite3 --output migration/vap.snapshot.json. The command opens the source read-only, creates a consistent create-only backup and publishes the versioned olympus.legacy-vap-snapshot 1.0.0 inventory. It records source/backup digests, counts, deterministic migration keys and explicit state decisions without creating native jobs. Active rows are blocked, ambiguous states remain unmapped, and targets/query secrets are excluded from the inventory; only the target digest remains. Consent, audit and product-analytics contents stay only in the backup pending separate privacy and provenance reviews. Existing outputs and symlinks are refused.

Before a future converter consumes the snapshot, verify the three artifacts together with olympus themis legacy-verify --source vap.db --backup migration/vap.backup.sqlite3 --manifest migration/vap.snapshot.json. The read-only check fails if any artifact changed, the contract is not exactly the supported version, SQLite integrity fails, or the inventory reconstructed from the backup differs. Success neither authorizes nor imports a scan.

Next create the non-executable review plan with olympus themis legacy-plan --source vap.db --backup migration/vap.backup.sqlite3 --manifest migration/vap.snapshot.json --output migration/vap.conversion-plan.json. The olympus.legacy-vap-conversion-plan 1.0.0 contract binds the plan to the manifest and backup digests, then classifies each row as a terminal record for review or retained because it is active, deleted, ambiguous, or lacks a native adapter. It contains no plaintext target, inherits no legacy authorization and explicitly creates zero executable jobs. The create-only, owner-only plan is not an import; a later SEC-A step still needs a current signed engagement manifest and a separate reviewed conversion command.

Approve only explicitly reviewed keys with olympus themis legacy-approve, passing the snapshot, plan, current signed engagement manifest, pinned approver public key, one or more --migration-key values, and a create-only output path. The olympus.legacy-vap-import-approval 1.0.0 receipt re-verifies the snapshot and plan plus Ed25519 signature, optional revocations, time window, technique, scope and target limit. It accepts only review_terminal entries and exposes digests rather than plaintext targets. It creates zero jobs and explicitly does not claim retroactive authorization for historical execution.

Finally run olympus themis legacy-import with the same snapshot, plan, approval, signed manifest and pinned key, plus the native database and a create-only receipt path. The command re-verifies the full chain, revocation and current scope before atomically writing idempotent terminal records with authorized=false; workers can never claim them. Legacy completed becomes native partial, never succeeded, because untrusted finding/configuration bodies stay in the immutable backup and only their digests are carried forward. failed and canceled remain distinct. Sensitive URL query values are redacted before native persistence.
