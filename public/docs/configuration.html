Configurazione Olympus

Olympus risolve ogni valore con questa precedenza, dalla più alta alla più bassa:

  1. opzione passata esplicitamente dalla CLI o dal chiamante;
  2. variabile OLYMPUS_<SEZIONE>_<CHIAVE>;
  3. valore nel file TOML selezionato;
  4. default integrato.

Per esempio, [http].timeout può essere sovrascritto da OLYMPUS_HTTP_TIMEOUT. Un'opzione CLI specifica del comando prevale su entrambi.

Il file viene cercato in quest'ordine:

  1. percorso indicato da OLYMPUS_CONFIG;
  2. ./olympus.toml;
  3. ~/.olympus.toml.

Se OLYMPUS_CONFIG indica un file assente o non valido, Olympus interrompe l'operazione: non ripiega silenziosamente su un altro file o sui default.

Validazione

olympus config validate
olympus config validate --file /percorso/olympus.toml

Il comando restituisce un documento JSON con sorgente, nomi degli override environment attivi e configurazione effettiva. I valori associati a chiavi sensibili (token, password, secret, api_key e simili) vengono sempre sostituiti con [REDACTED].

Gli override environment sono convertiti nel tipo del valore previsto e validati con gli stessi limiti del TOML. Un valore non interpretabile o fuori intervallo causa exit code 2.

Le opzioni HTTP riconosciute sono timeout, deadline, retries, backoff, jitter, rate, max_response_bytes, max_response_headers, max_response_header_bytes, max_redirects, max_decompressed_bytes e max_expansion_ratio.

La tabella [observability] è opzionale e usa gli stessi criteri di precedenza. Le opzioni riconosciute sono backend (none, prometheus, otlp), cardinality_limit (8–256), service_name, otlp_endpoint e prometheus_textfile. Il default none non carica dipendenze, non invia dati e non apre listener. Configurazione dei backend, metriche e confini di redazione sono descritti in Observability / Osservabilità.

Due file, due scopi

olympus.toml (questo documento) configura il client HTTP condiviso e l'osservabilità operativa opzionale. I bound di esecuzione — timeout, deadline, concorrenza, retry, backoff, intervallo minimo, jitter — e il profilo lab vivono invece in un file separato, olympus.policy.toml, con una propria catena di discovery (OLYMPUS_POLICY → ./olympus.policy.toml → ~/.olympus/policy.toml) e i propri comandi olympus policy show|validate|diff|edit.

La separazione è voluta: un file descrive come si parla HTTP, l'altro descrive quanto lavoro è autorizzato in questo engagement e verso quale perimetro. Vedi policy di esecuzione editabile.

Segreti e credenziali (SecretProvider, SEC-D)

I segreti a runtime (API key OSINT, token di servizio) non sono risolti con letture sparse di os.environ, ma attraverso un'unica porta iniettabile, olympus.core.secrets.SecretProvider, così una installazione può continuare a usare le variabili d'ambiente come fallback locale oppure collegare un backend più robusto senza toccare i punti di chiamata.

  • EnvSecretProvider (default) legge le variabili d'ambiente vive del

processo; un valore assente, vuoto o di soli spazi conta come non impostato. Non viene mai caricato automaticamente un file .env.

  • KeyringSecretProvider legge dal keyring del sistema operativo. È un backend

opzionale: l'import di keyring è isolato e, se il pacchetto non è installato, la costruzione solleva SecretProviderUnavailable (il core non dipende da keyring). Installalo a parte per abilitarlo.

  • ChainSecretProvider((keyring, env)) prova i provider in ordine e restituisce

il primo segreto trovato — tipicamente keyring con l'ambiente come fallback.

Il valore risolto è un pydantic.SecretStr: resta mascherato in repr, log e traceback e viene estratto con .get_secret_value() solo nel punto esatto di utilizzo. Esempio di adozione: i client OSINT di Argus (NumverifyClient.from_env, RapidApiMessagingClient.from_env) accettano un secrets: SecretProvider opzionale e, per default, risolvono OLYMPUS_NUMVERIFY_KEY / OLYMPUS_RAPIDAPI_KEY dall'ambiente.

OIDC multiutente offline-first

Themis può affiancare alle API key un bearer OIDC senza contattare il provider durante le richieste. L'operatore fissa issuer HTTPS, audience e JWKS locale:

olympus themis api --identities .olympus/identities.json \
  --oidc-issuer https://identity.example.test \
  --oidc-audience olympus-control-plane \
  --oidc-jwks /etc/olympus/issuer.jwks.json

Discovery e download remoto del JWKS sono disabilitati. Sono accettate solo firme asimmetriche RS256, ES256 o EdDSA, con kid univoco e durata del token non superiore a un'ora. Il claim sub identifica una voce del registro locale: scope per azione, scadenza, rate limit e revoca provengono sempre da quel registro e una revoca ha effetto senza riavvio. Il bearer non viene mai scritto nell'audit. La rotazione uniforme delle credenziali resta tracciata in ROADMAP.md sotto SEC-D.
