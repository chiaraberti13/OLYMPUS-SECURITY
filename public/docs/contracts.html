Olympus versioned contracts

This document is the wire/storage compatibility policy for every Olympus producer, CLI, worker, database adapter, API, and report consumer.

The physical SQLite schema version (PRAGMA user_version) is separate from document contract versions. Athena, engagements and finding-transition stores upgrade unversioned legacy databases transactionally to physical schema 1 and reject newer versions. Themis job storage maintains its own physical version.

The UI↔API contract-surface test holds each one byte-identical to what the API serves (ARCH-4).

The authoritative JSON Schemas are generated by:

olympus core export-schemas ./schemas

The export creates a deterministic, versioned catalog:

  • catalog.json records each contract's identity, direction (input, output,

or shared), SemVer, path, and SHA-256 digest;

  • contracts/<schema_name>/<MAJOR.MINOR.PATCH>.schema.json is the publishable

JSON Schema Draft 2020-12 document with a stable $id;

  • schemas.json preserves the previous flat bundle for existing consumers.

Files below schemas/ are committed. make schemas-check regenerates the catalog in memory and fails when a Pydantic model changes without updating the published artifacts or its contract version.

Compatibility rules

  1. Every new persisted or exchanged document carries an exact schema_name

and a MAJOR.MINOR.PATCH schema_version string.

  1. Consumers reject the wrong schema name, malformed versions, a different

major version, or a newer minor version. Patch differences are compatible.

  1. Models reject unknown fields. A minor release may therefore add only

optional fields that an updated consumer knows; it must not reinterpret or remove existing fields. Breaking changes require a new major version and an explicit migration/adapter.

  1. Nested contracts are validated too. A compatible collection envelope does

not excuse an incompatible Asset, Finding, Alert, or ScanJob.

  1. Consumers fail with an actionable compatibility error. They never drop an

invalid item, invent a default interpretation, or silently coerce a future major version.

  1. Producers write canonical current-version documents. Legacy inputs are

accepted only through a named, tested adapter and are re-emitted in the current format.

Persisted scope, plan, job, evidence and CTI case upgrades use the central olympus.core.migrations registry. Operators can inspect every supported edge:

Every edge is pure, ordered and covered by committed legacy fixtures. Running a migration twice returns the same current document. A wrong identity, partial header, ambiguous legacy fields, unsupported future version, missing edge or incomplete evidence fails with an explicit error; migrations never fabricate a digest, authorization, timestamp, indicator or finding.

Current legacy adapters

  • Athena plans created before SemVer either omitted both header fields or used

integer schema_version: 1. load_plan maps these two known shapes to olympus.athena.plan 1.0.0; partial/ambiguous headers remain invalid.

  • Apollo maps the former rule shape only when both header fields are absent.

Legacy events likewise require both headers to be absent and all five identity fields to be present; no event ID or timestamp is synthesized. Partial headers, catch-all rules, duplicate rule IDs, and conflicting duplicate event IDs fail.

  • Minerva verifies custody 1.0.0 through a named read-only adapter. That format

links event metadata but not the evidence SHA-256, so verify/timeline warn with exit 1 and append is refused. New 2.0.0 entries hash the evidence digest; converting old history would invent unavailable provenance and is not allowed.

  • Vulcan still accepts the original bare arrays or single shared objects as an

input compatibility path. Versioned Argus, Helios, Apollo, and security-report envelopes are validated before their arrays are consumed. Security-report 1.0.x is normalized by a named additive adapter to 1.1.0 with an empty authorization-provenance array; newer minor/major documents fail closed.

  • No compatibility claim is made for unversioned Athena result documents. New

writes and database reads validate olympus.athena.result and its nested job, asset, and finding contracts.

Migration adapters must be pure, deterministic, covered by fixtures from the old version, and removed only after the announced compatibility window.

Run make test-contract to detect drift. After reviewing and classifying an intentional interface change, regenerate the fixtures with:

make contract-goldens

A fixture update alone does not make a breaking change compatible. The same commit must update the affected contract SemVer, migration or adapter, schema catalog, changelog and documentation as required by the rules below.

Support and deprecation window

  • From the first tagged release, a consumer supports the current minor release

and the immediately preceding minor release of the same major for at least six months after the newer minor is published. Patch releases remain wire compatible within their minor line.

  • A deprecation is announced in the changelog and contract documentation. When

the surface supports it, CLI stderr or API Deprecation and Sunset headers also identify the replacement and removal date.

  • A deprecated field or shape is not removed before both the six-month window

has elapsed and the next major release is available. Removal requires a major contract version and an explicit migration or compatibility adapter.

  • A critical security defect may require an earlier removal. Such an exception

is documented in a security advisory with the safe replacement and migration instructions; unsafe input is never accepted merely for compatibility.

  • Before the first tagged release, no calendar support guarantee is implied, but

every committed schema and golden remains a blocking compatibility boundary.

Security properties

Contract validation happens before persistence or cross-module processing. Unknown fields cannot smuggle command strings, credentials, or provider-specific options into jobs/plans. Schemas identify structure, not authorization: callers must still enforce engagement scope, approval, redaction, and execution policy.
