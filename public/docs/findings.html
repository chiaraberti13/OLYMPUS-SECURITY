Findings and vulnerability intelligence

A finding is Olympus's record of a weakness, vulnerability or misconfiguration attached to an asset. Every assessment module (Artemis, Helios, Themis, …) produces findings against the same olympus.finding contract, and every consumer (Athena, Vulcan, the report and PDF renderers) reads that one contract — there is no per-module finding shape.

Contract

olympus.finding (src/olympus/core/models.py) carries the descriptive core — finding_id, asset_id, source, title, description, severity, status, cvss, evidence, remediation, references, timestamps — plus an additive layer of structured vulnerability intelligence (ROADMAP WEB-C):

FieldTypeMeaning
cvelist[str]Canonical CVE ids, e.g. ["CVE-2021-44228"].
cwelist[str]Canonical CWE ids, e.g. ["CWE-502"].
epss`float \None`FIRST EPSS exploit probability in [0, 1].
epss_percentile`float \None`EPSS percentile in [0, 1].
kevboolListed in the CISA Known Exploited Vulnerabilities catalogue.
confidence`Confidence \None`Analyst confidence the finding is a true positive (low/medium/high).

These fields are optional with defaults, so the contract stays at schema_version 1.0.0: a finding persisted before WEB-C (without any of them) still validates, and the new fields simply default to empty/unset.

Why these fields

CVSS tells you how bad a vulnerability is if exploited; it says nothing about whether anyone is exploiting it. Risk-based triage needs both:

  • CVE — Common Vulnerabilities and Exposures, the

public catalogue id. Olympus links each CVE to the NIST NVD detail page in reports.

  • CWE — Common Weakness Enumeration, the weakness

class (e.g. CWE-79 Cross-site Scripting). Linked to the MITRE definition.

  • EPSS — FIRST Exploit Prediction Scoring System:

a daily probability (0–1) that a CVE will be exploited in the next 30 days.

  • KEV — CISA Known Exploited Vulnerabilities:

confirmed in-the-wild exploitation; the strongest "fix this now" signal.

Validation (Pydantic v2 field validators — see the official Pydantic validators docs): cve/cwe entries are upper-cased and must match the CVE-YYYY-NNNN(NNN) / CWE-N patterns; epss and epss_percentile must lie in [0, 1]. A malformed id or an out-of-range probability raises a ValidationError.

Structured first, free text as a fallback

Two helper methods resolve a finding's identifiers:

finding.cves()  # -> sorted, de-duplicated CVE ids
finding.cwes()  # -> sorted, de-duplicated CWE ids

Each helper returns the structured field when it is set; otherwise it falls back to scanning the finding's free text (title, description, references, evidence) with the CVE/CWE regexes. This keeps pre-WEB-C findings — where a scanner only mentioned CVE-2021-44228 in prose — working exactly as before, while letting newer producers populate the structured fields directly.

Example. A finding whose title says "mentions CVE-2000-1111" but whose cve field is ["CVE-2021-44228"] resolves to ["CVE-2021-44228"]: the structured field wins, and the stray text id is ignored.

Contextual risk score

Finding.risk_score() returns a single scalar in [0, 100] that blends the finding's fields in the same priority order Vulcan uses to rank findings (KEV > EPSS > CVSS > severity, see olympus.vulcan.enrichment.prioritize), so a UI or report can sort and threshold on one number:

  • base = cvss × 10 when a CVSS is present, else a severity band

(info 10, low 30, medium 50, high 75, critical 90);

  • CISA KEV membership (confirmed in-the-wild exploitation) raises the score

to at least 95 — it dominates everything else;

  • otherwise EPSS (predicted exploitation probability) lifts the floor to

epss × 100, so a likely-exploited finding outranks a merely severe one;

  • confidence is a mild modifier only (high +5, low −10): it nudges, it

never decides.

It is computed on demand from the current fields — never stored, so never stale, and no addition to the wire/storage contract. The PDF report shows it on each finding's metadata line (Risk NN/100).

finding.risk_score()  # e.g. 95.0 for a KEV-listed CVE, 30.0 for a quiet low finding

Lifecycle state machine

A finding is not static: it is triaged, confirmed or dismissed, remediated, accepted as a known risk, or re-opened on recurrence. core/finding_lifecycle.py is the single source of truth for which FindingStatus changes are legal, so CLI, TUI, API and the Web UI enforce the same workflow rather than letting any code set status to any value.

The transitions are defined over the existing seven FindingStatus states (no new states, so no schema change):

FromMay move to
newtriaged, confirmed, false_positive, accepted, closed
triagedconfirmed, false_positive, accepted, closed
confirmedin_remediation, accepted, false_positive, closed
false_positiveconfirmed (only, if it turns out real)
acceptedconfirmed, closed
in_remediationclosed (retest-gated, see below), confirmed (retest failed), accepted
closedconfirmed (recurrence)

A transition to the same status is rejected, so a no-op never masquerades as a workflow step.

from olympus.core.enums import FindingStatus
from olympus.core.finding_lifecycle import transition, can_transition

if can_transition(finding.status, FindingStatus.CONFIRMED):
    finding = transition(finding, FindingStatus.CONFIRMED)  # returns an updated copy

transition(finding, target) returns a copy with the new status and a refreshed last_seen (the original is untouched); an illegal move raises FindingTransitionError naming both states.

Closing requires the evidence of a retest (VAL-2)

closed means resolved — the one honest basis for that claim is a retest that could no longer reproduce the issue. So closing is not done through the generic path: transition and record_transition refuse any move to closed and point the caller at close_after_retest. can_transition still lists closed as structurally reachable (the re-open-on-recurrence semantics stay honest); the evidence gate lives in the application functions, enforced identically by the CLI and the Web UI.

from olympus.core.finding_lifecycle import close_after_retest

# retest_evidence must be a REAL reference: an olympus.evidence custody id
# (EVD-YYYY-NNNNN) or a SHA-256 digest — never free text, or the close is
# refused (fail-closed) and nothing changes.
finding, record = close_after_retest(
    finding, actor="qa", retest_evidence="EVD-2026-00009", reason="retest could not reproduce it"
)
# record.retest_evidence is stored in the immutable audit ledger, so a report can
# answer "closed on the strength of which evidence?". A *failed* retest is not a
# close: move the finding back to `confirmed` via record_transition (no gate).

From the terminal, olympus vulcan transition --to-status closed requires --retest-evidence; in the Web UI the finding detail page asks for the retest evidence before it will record a close. The authorized simulations that can produce such retest evidence (and the reproducible lab behind them) are tracked under VAL-2/PURPLE-1/PURPLE-2; this gate is the lifecycle half that refuses an unproven close.

Audit trail

A finding carries only its current status; the durable trail of how it got there lives in append-only olympus.finding-transition records. Use record_transition to apply a move and capture its audit record together:

from olympus.core.enums import FindingStatus
from olympus.core.finding_lifecycle import record_transition
from olympus.findings.store import SqliteFindingTransitionStore

moved, record = record_transition(
    finding, FindingStatus.ACCEPTED, actor="analyst@team", reason="accepted risk until Q3"
)
store = SqliteFindingTransitionStore(Path("./workspace/finding_transitions.db"))
store.append(record)  # append-only, owner-only (0600)
store.history(finding.finding_id)  # every transition, oldest first

Each FindingTransition records from_status, to_status, actor, an optional reason (the rationale for a suppression or accepted-risk decision), occurred_at, and the finding's engagement_id. The store is append-only: records are inserted, never replaced or deleted, so the history cannot be rewritten through the API (a duplicate transition_id is rejected). This answers "who accepted this risk, and when?" without trusting the mutable finding.

Set OLYMPUS_FINDINGS_ENCRYPTION_KEY to a random value of at least 32 characters to encrypt each transition document with authenticated encryption. The key is resolved through SecretProvider and is never stored in SQLite. Identifiers and ordering timestamps remain queryable, while actor, reason, engagement and status details are ciphertext. Existing plaintext rows remain readable during migration; encrypted rows fail closed if the key is missing, wrong or the ciphertext was changed.

Encrypting finding bundles at rest

The immutable core.Finding/core.Asset JSON bundles that producers (the scanners, Athena) emit and the CLI and Web UI review can also be stored encrypted, protected by the same OLYMPUS_FINDINGS_ENCRYPTION_KEY resolved through SecretProvider — one key for findings at rest wherever they live, never written into the ciphertext.

# Encrypt a bundle produced by a scan for storage at rest:
olympus vulcan encrypt-bundle -i findings.json -o findings.enc.json
# ...and decrypt it again for export or migration:
olympus vulcan decrypt-bundle -i findings.enc.json -o findings.json

Encryption is transparent on read: every loader (olympus vulcan rank | report | diff | trend | ... and the Web UI findings pages) detects the envelope and decrypts it in place when the key is set, so an encrypted bundle needs no separate decrypt step before review. A plaintext bundle keeps loading unchanged, so enabling encryption never strands bundles written earlier. Reads are fail-closed: an encrypted bundle presented with no key, a wrong key or a tampered ciphertext is rejected rather than shown as empty or partial results.

Suppression

Suppressing a finding (accepting the risk, or dismissing it as a false positive) removes it from the active worklist, so Olympus refuses to do it silently — a justification is required:

from olympus.core.enums import FindingStatus
from olympus.core.finding_lifecycle import suppress, unsuppress, is_suppressed

moved, record = suppress(finding, actor="analyst@team", reason="accepted until Q3")
# or dismiss as a false positive:
moved, record = suppress(
    finding,
    actor="analyst@team",
    reason="duplicate of FND-X",
    as_status=FindingStatus.FALSE_POSITIVE,
)
is_suppressed(moved)  # True  (status in {accepted, false_positive})
reopened, record = unsuppress(moved, actor="analyst@team", reason="resurfaced on retest")

suppress requires a non-empty reason and a suppression target status (accepted or false_positive); unsuppress re-opens a suppressed finding to confirmed. Both go through the lifecycle state machine and produce an audit record, so a suppression is always both legal and justified.

Cross-scanner deduplication

Two scanners often report the same vulnerability on the same asset with different finding_ids. vulcan.aggregate.merge_duplicate_findings collapses those into one finding without losing evidence (a WEB-C completion criterion):

  • Identity. Findings are grouped by (asset_id, vulnerability), where the

vulnerability is the set of CVEs when any are known (structured or text-derived), else the normalized title. This is conservative: with no shared CVE, only identical titles merge, so distinct issues are never collapsed.

  • Lossless merge. Evidence, references, CVE and CWE ids are unioned; the most

urgent signal wins for each scalar (max severity, CVSS, EPSS; KEV if any source saw it; highest confidence). The representative (highest severity, then risk, then stable id) supplies the title, description, remediation, status and id; timestamps widen to the group's real span.

It runs in the Vulcan aggregation pipeline after the exact-id dedupe_findings, and is stable and idempotent (a finding with no duplicate passes through unchanged).

Scan comparison (WEB-I)

A security programme is judged by what changes between runs. vulcan.compare is the single, tested place that compares two finding sets and classifies each logical issue as new, resolved or persistent:

  • Logical identity. Findings are matched by the same

(asset_id, vulnerability) fingerprint used by the dedup (vulcan.aggregate.finding_fingerprint), never by the per-run finding_id, so the same issue seen in two runs is recognised as one. Each side is folded with merge_duplicate_findings first, so a logical issue counts once.

  • Classification. diff_findings(baseline, current) returns a ScanDiff

with the new (regressions or newly discovered), resolved (the evidence a remediation worked) and persistent findings; persistent entries carry both representatives so a severity or risk change is visible (severity_worsened, risk_delta). The result is pure, offline and deterministic (ranked by risk).

# Compare two runs of the same scope. Exit code 1 when the current run
# introduced any new finding (a regression), 0 when it did not.
olympus vulcan diff --baseline run-2026-09.json --current run-2026-10.json

# --format json emits the full summary + new/resolved/persistent projection.
olympus vulcan diff --baseline run-2026-09.json --current run-2026-10.json --format json

The browser exposes the same engine at GET /findings/diff when the control plane is started with a --baseline-directory alongside --findings-directory; see web.md.

A report can also ship the comparison: olympus vulcan report --compare-baseline BASELINE --compare-output diff.json writes a companion scan-diff (same diff_findings core) classifying the report's own ranked findings against the baseline run — a comparative Vulcan report (VAL-1). The two flags must be used together.

Attack-surface (asset) diff — VAL-1

diff_assets(baseline, current) is the asset counterpart of the finding diff: it classifies every olympus.asset across two snapshots as new (the attack surface grew), removed, or persistent, matched by logical identity (asset_id) and folded with dedupe_assets so a duplicate counts once. Persistent assets carry both representatives, exposing criticality_changed and attack_surface_changed (the reachable surface — type, hostname, sorted IPs — differs). Pure, offline and deterministic (ordered by asset_id).

# Compare two asset snapshots of the same scope. Exit code 1 when the current
# snapshot expanded the attack surface (introduced any new asset), 0 otherwise.
olympus vulcan asset-diff --baseline assets-2026-09.json --current assets-2026-10.json

# --format json emits the full summary + new/removed/persistent projection.
olympus vulcan asset-diff --baseline a.json --current b.json --format json

Trend across several runs

vulcan.trend.build_finding_trend generalises the two-run diff to an ordered series: given snapshots oldest first, it reports each run's folded total and severity breakdown and — between consecutive runs — how many findings were new, resolved or persistent (reusing diff_findings). It is pure, offline and deterministic.

# Finding severity trend across three runs (oldest first). Exit code 1 when the
# most recent run introduced any new finding (a regression), 0 otherwise.
olympus vulcan trend \
  --snapshot run-2026-08.json \
  --snapshot run-2026-09.json \
  --snapshot run-2026-10.json

# --format json emits the full per-point projection for dashboards.
olympus vulcan trend --snapshot run-2026-08.json --snapshot run-2026-10.json --format json

Lifecycle across the history — reappeared findings (VAL-1)

A two-run diff cannot tell a genuinely new finding from one that was fixed and has come back. vulcan.lifecycle.classify_lifecycle classifies the latest snapshot's logical findings against the whole ordered history:

  • new — never seen before this run;
  • persistent — also present in the immediately previous run (still open);
  • reappeared — present now, absent in the previous run, but seen in an earlier

run — i.e. resolved and returned (it carries how long it was absent_for and the severity delta from when it was last seen);

  • resolved — in the previous run but not the latest.

"Reappeared" is derived from history and the shared logical identity — it is not a new canonical lifecycle state on the finding (see the state machine above). The engine reuses the same identity, folding and risk ordering as the diff/trend, so every surface agrees. It is pure, offline and deterministic.

# Classify the latest run against the full history (snapshots oldest first). Exit
# code 1 when the latest run introduced any new OR reappeared finding, 0 otherwise.
olympus vulcan lifecycle \
  --snapshot run-2026-08.json \
  --snapshot run-2026-09.json \
  --snapshot run-2026-10.json

# --format json emits the full projection (new / persistent / reappeared / resolved).
olympus vulcan lifecycle --snapshot run-2026-09.json --snapshot run-2026-10.json --format json

Comparative report across the history (VAL-1)

For a recurring programme the lifecycle and the attack-surface diff are usually read together: since the last assessments, what got worse, what was fixed, and did the reachable surface grow? vulcan.comparative.build_comparative_report assembles both into one human-readable document, reusing the two engines verbatim rather than deriving a parallel one — the finding lifecycle over the whole history, plus the optional asset-surface diff between a baseline and a current snapshot. It is pure, offline and deterministic; target-controlled text (titles, hostnames) is escaped through the same tested Markdown neutraliser the single-run report uses, so a finding title cannot forge report structure or a clickable link.

The report regresses — exit code 1 — when the latest state is worse: a new or reappeared finding, or a grown attack surface. The Markdown form is the default (a report is made to be read); --format json emits a versioned olympus.comparative-report document that embeds the vulcan lifecycle and vulcan asset-diff projections field-for-field, so a consumer can pin the shape.

# Markdown report (default) to stdout; add --output PATH to write a file.
olympus vulcan comparative-report \
  --snapshot run-2026-08.json \
  --snapshot run-2026-09.json \
  --snapshot run-2026-10.json \
  --engagement "ACME Q4"

# Include the attack-surface diff (pass both baseline and current asset snapshots).
olympus vulcan comparative-report \
  --snapshot run-2026-09.json --snapshot run-2026-10.json \
  --asset-baseline assets-2026-09.json --asset-current assets-2026-10.json

# Machine-readable, versioned document.
olympus vulcan comparative-report \
  --snapshot run-2026-09.json --snapshot run-2026-10.json --format json

The recurring execution of these assessments — scheduled, with preflight and signed evidence — belongs to the Execution Engine (API-3) and is tracked separately; this command is the offline comparison over snapshots already produced.

Explainability — why a finding, why this risk (EXPL-1)

vulcan.explain.explain_finding builds a shared data contract (FindingExplanation) that answers, the same way on every surface, why is this a finding, why this severity, and how sure are we? It is the single place that derives that answer, so the CLI, the API and the reports agree by construction (EXPL-2 wires them to this one core — no explanation logic duplicated in a frontend).

The explanation is derived only from the finding's own stored fields: it performs no scanning, opens no network and invents nothing. It is a versioned contract (olympus.finding-explanation 1.0.0), and every claim carries an epistemic class (core.enums.EpistemicClass, shared with correlation CORR-1) so a weaker claim is never shown as a stronger one:

  • observed_evidence — what the finding actually carries (attached evidence,

confirmed KEV exploitation, CVSS, EPSS, and CVE/CWE ids from a structured field);

  • inference — a claim derived by reasoning, e.g. a CVE/CWE id *parsed from

free text* (weaker than a structured identifier, so labelled as such);

  • deterministic_result — the contextual risk score, a pure computation over

the fields above (never presented as an observation);

  • suggested_correlation — an ATT&CK technique mapped from the finding's CWE

via the reviewed vulcan.attack CWE→ATT&CK table (the technique an attacker would use against this weakness class, not observed exploitation); carried both as a classified statement and in a structured attack list with provenance (automatic/reviewed), confidence and rationale;

  • unverified_hypothesis completes the taxonomy for CORR-1 / future classes.

Alongside the classified statements it carries:

  • risk factors — how the score was reached, reproduced from the same

constants the score itself uses (SEVERITY_RISK_BASE, KEV_RISK_FLOOR, CONFIDENCE_RISK_MODIFIER in core.models), so the score and its explanation can never diverge. Exactly one factor is marked decisive — the base, or a KEV/EPSS floor only when it truly rose above the base — so the text never claims an escalation that did not change the number;

  • limits — explicit caveats (no CVSS, CVE/CWE parsed from free text, no

evidence attached, low or missing confidence).

# Explain each finding (descending risk). Human text blocks, or --format json for
# the full contract that the API and reports also render.
olympus vulcan explain --input findings.json
olympus vulcan explain --input findings.json --format json

The same core backs every surface (EXPL-2):

  • API — POST /api/v1/vulcan/explain (scope findings:read) takes one

olympus.finding and returns the identical olympus.finding-explanation contract; a pure, offline transform that opens no network.

  • Report — olympus vulcan report --explanations PATH writes a companion

olympus.finding-explanations document (versioned, one explanation per reported finding, in the report's ranked order) alongside the JSON report, without changing the report model.

A parity test pins the CLI, the API, the report companion and explain_finding to the same output for the same finding, so no surface can drift.

# Build the report and the matching explanations companion in one run.
olympus vulcan report --engagement Acme --findings findings.json \
  --output report.json --explanations explanations.json

Portability — findings and assets as NDJSON (WEB-J)

Findings and assets move between installations and line-oriented tools as portable, versioned NDJSON (one record per line, each the deterministic olympus.finding / olympus.asset document). vulcan.portable is the single, tested place that serialises and parses them: export is sorted by id (diffable, round-trip-verifiable) and import is strict and all-or-nothing — the whole file is validated against the contract before anything is written. It round-trips losslessly with the JSON bundles the loaders already consume.

# JSON bundle -> portable NDJSON (sorted, deterministic)
olympus vulcan export --kind findings -i findings.json -o findings.ndjson
olympus vulcan export --kind assets   -i assets.json   -o assets.ndjson

# portable NDJSON -> canonical JSON bundle (loadable by every Olympus tool)
olympus vulcan import --kind findings -i findings.ndjson -o restored.json

A malformed or contract-incompatible NDJSON file exits 2 (usage) and writes nothing.

Importing third-party SARIF (WEB-J)

SARIF 2.1.0 is the interoperability format for analysis results, so Olympus can ingest any SARIF-producing tool's findings and run them through the same lifecycle, dedup, diff, trend and reporting as native findings (Hermes already exports SARIF; vulcan.sarif is the import side). The document comes from an external tool, so it is treated as hostile input: strict 2.1.0 validation, type-checked fields, bounded sizes, and a malformed document imports nothing.

# SARIF report -> canonical core.Finding bundle, linked to an Olympus asset
olympus vulcan sarif-import -i report.sarif.json -o findings.json \
  --asset-id AST-2026-00001

# core.Finding bundle -> SARIF 2.1.0 for any SARIF consumer (CI code-scanning…)
olympus vulcan sarif-export -i findings.json -o report.sarif.json

The SARIF level maps to severity (error→high, warning→medium, note→low, none→info; absent→medium, never silently downgraded); ruleId and the rule's helpUri become references; each result location becomes uri:line evidence. Imported findings are stamped source=manual (ingested from outside Olympus) unless --source is given.

Export is the symmetric direction (deterministic, sorted by finding id). Severity maps to the SARIF level and — because SARIF has four levels while Olympus has five severities, so critical and high both become error — the exact severity, provenance, status, risk score and CVE/CWE/KEV ride in each result's properties bag, so a SARIF-aware consumer keeps the detail and a re-import loses nothing but that four-level collapse.

Tagging, search and filters

Findings carry free-form tags (operator labels for triage and grouping — additive and optional, like Asset.tags; trimmed, de-duplicated and emptied of blanks on validation). vulcan/search.py is the single, tested place that decides what a filter means, so the CLI, TUI and Web UI narrow findings the same way.

FindingFilter is an immutable value object; every criterion is optional and an unset one does not constrain the result:

CriterionMatches when
statusesthe finding's status is in the set
sourcesthe finding's source is in the set
min_severityseverity ≥ the threshold
engagement_idthe finding is linked to that engagement
kev_onlythe finding is KEV-listed
has_cvethe finding has (or lacks) any CVE
tagsthe finding carries all these tags (case-insensitive)
textcase-insensitive substring over title, description, references, CVE/CWE, tags and the asset/finding ids
min_risk_scorerisk_score() ≥ the threshold
from olympus.core.enums import FindingStatus, Severity
from olympus.vulcan.search import FindingFilter, search_findings

query = FindingFilter(
    statuses=frozenset({FindingStatus.CONFIRMED}),
    min_severity=Severity.HIGH,
    kev_only=True,
)
urgent = search_findings(all_findings, query)  # AND semantics, input order kept

Criteria combine with AND; search_findings preserves input order (rank separately with rank_findings or risk_score).

Finding view

Browsing findings — in the CLI, the TUI or the Web UI — must show the same columns, derive them the same way, and be honest about absence: a datum the finding does not carry (no CVSS yet, no EPSS overlay, no remediation written) is not the same as a present-but-empty one, and must never render as a fabricated 0 or a blank that reads like "none found". vulcan/view.py is the single, tested place that projects an olympus.finding into presentation-ready values (the same "one source of meaning" principle search.py applies to filtering):

from olympus.vulcan.view import FindingView, rank_by_risk

view = FindingView(finding)
view.row()  # compact one-line cells for a table (LIST_COLUMNS)
view.display_items()  # ordered (label, value) pairs for a detail view
view.detail()  # full JSON-serialisable projection (absent scalars stay None)
ordered = rank_by_risk(findings)  # descending risk_score, stable for ties

A missing scalar is kept as None in detail() (machine types preserved) and rendered as — (view.ABSENT) in row()/display_items(), so every interface can tell absent from empty. The view carries the full WEB-C column set — title, severity, status, asset, source, CVE, CWE, CVSS, EPSS, CISA KEV, confidence, evidence, first/last seen, remediation, references, tags — plus the contextual risk_score. There is no separate scanner field on the contract: source is a finding's provenance (the producing engine, e.g. themis), so it carries that column.

CLI

olympus vulcan findings reuses the filter and the view, so the CLI narrows and renders findings exactly like the TUI and Web UI will:

# List, filtered and ordered by descending risk (absent data shown as "—")
olympus vulcan findings list --findings findings.json --kev-only --min-severity high

# Any FindingFilter criterion is a flag: --status, --source, --engagement,
# --has-cve/--no-cve, --tag (repeatable), --text, --min-risk. --format json
# emits the full detail() projection for scripting.
olympus vulcan findings list --findings findings.json --format json

# Inspect one finding with every column
olympus vulcan findings show FND-1234 --findings findings.json

Evidence browser

A finding is only as trustworthy as the material behind it, so an operator must be able to walk from a finding to its evidence — and judge whether that evidence is tamper-evident — identically from the CLI, the TUI or the Web UI. vulcan/evidence_view.py is the single, tested place that projects a finding's evidence list into a navigable view, reusing Minerva's chain of custody (the same "one source of meaning" principle view.py applies to columns and search.py to filters).

Two kinds of evidence reference can appear on a finding:

  • a structured reference EVD-YYYY-NNNNN that names an olympus.evidence

record and, through Minerva, a tamper-evident chain of custody — its digest, the collection/transfer/analysis/archive events, and the ledger's signature state;

  • an inline snippet an adapter attached directly (scanner=nmap, url=...),

which is target-influenced free text.

Everything is defanged. Inline snippets and resolved URIs are stripped of terminal control sequences and passed through redact_text (so a hostile target cannot rewrite the operator's terminal or leak a query secret — see SEC-H), and the raw bytes an evidence reference points at are never read or printed — only the digest and custody metadata. Absence is told honestly: an evidence id with no custody record renders as no-custody, a digest that disagrees with the ledger as digest-mismatch, and an unsigned or unverified ledger says so rather than showing a reassuring blank.

The chain-of-custody signature surfaced here is the Minerva ledger's HMAC-SHA256 head signature; a verified custody timeline can additionally be exported and Ed25519-signed with olympus minerva timeline --export --sign-key for third-party verification.

from olympus.vulcan.evidence_view import build_finding_evidence_view

view = build_finding_evidence_view(
    finding,
    custody_records=ledger_entries,  # verified Minerva custody entries (optional)
    evidence_records={evd.evidence_id: evd},  # olympus.evidence records (optional)
    signed=True,
    signature_verified=True,
)
view.rows()  # compact table cells, one per evidence reference
view.custody_signature()  # "HMAC-SHA256 signature verified", "unsigned", ...
view.detail()  # full JSON-serialisable projection
# Browse one finding's evidence against the verified custody ledger.

Notifications (WEB-I)

A defender should not have to open a dashboard to learn a finding landed. The output port in src/olympus/core/notifications.py turns a core.Finding (or a core.ScanJob) into a small, versioned (olympus.notification 1.0.0), redacted payload and — only when explicitly configured — delivers it to an operator webhook. It is deliberately a port on the core, not a new module.

Three guarantees hold by construction:

  • Redacted, no secrets. Every human-readable field is run through

safe_terminal_text (one line, control characters stripped, URL credentials redacted) and every label through redact_mapping, the same discipline as audit logs and job records.

  • Off by default. Without --webhook the command only previews the payloads

and makes no network call; an empty NotificationDispatcher is a no-op.

  • SSRF-safe egress. The default PinnedWebhookPoster pins every hop to the

public-only global_address_policy, so a misconfigured or hostile URL cannot be turned into a request against cloud metadata or an internal service, and only http(s) schemes are dialled.

Two channels implement the NotificationChannel port: a WebhookChannel (JSON POST over the SSRF-safe transport) and an EmailChannel (a redacted plain-text message over smtplib). Both are off until explicitly configured; either or both can be enabled at once.

# Preview the redacted notifications for high+ findings (no network, off by default)
olympus vulcan notify --findings ./findings.json --min-severity high --format json

# Deliver each to an operator webhook (exit 5 if any delivery fails)
olympus vulcan notify --findings ./findings.json --webhook https://hooks.example/olympus

# Deliver each by e-mail (repeat --email-to for several recipients)
olympus vulcan notify --findings ./findings.json \
  --email-to soc@example.com --email-from olympus@example.com --smtp-host mail.example.com

The native Themis worker can emit the same redacted notification automatically when a job reaches a terminal state — still off by default and over the same SSRF-safe channels:

# Notify an operator webhook each time a job finishes (no channel => no network)
olympus themis workers --notify-webhook https://hooks.example/olympus

# Also emit one notification per finding at or above a severity (bounded)
olympus themis workers --notify-webhook https://hooks.example/olympus \
  --notify-finding-severity high

Only terminal jobs notify (a requeued retry does not); with --notify-finding-severity the worker additionally emits one redacted notification per finding at or above that severity, ordered most-severe first and capped so a noisy scan cannot flood the sink (malformed finding records are skipped, never raised). A delivery failure is reported rather than raised, and a notification problem can never crash the worker loop. Both the manual vulcan notify command and the worker use the same Iris port.
