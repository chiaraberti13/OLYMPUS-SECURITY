Vulcan ATT&CK associations / Associazioni ATT&CK Vulcan

Authenticated readers with findings:read can open /findings/attack from the ATT&CK navigation link. The page reads the configured findings directory and reuses Vulcan's versioned offline CWE mapping: technique, tactic, confidence, automatic provenance and rationale are shown beside links to each finding. Unmapped findings remain visible. All stored findings are included, regardless of lifecycle status. This is an association view, not evidence of exploitation or validated detection coverage. No network activity is performed. The dashboard summarises mapped findings and distinct techniques with a link to the evidence page; the card uses the same findings:read permission.

A missing store is distinguished from an empty one; unreadable inputs return HTTP 503 instead of a misleading empty analysis. The export returns HTTP 400 when no directory is configured. Invalid formats return HTTP 422.

Olympus exposes four interfaces over the same core use cases: the Typer CLI, the Textual TUI, the authenticated HTTP API (olympus.themis.api) and the browser web control plane (olympus.themis.web). None of them carries its own cybersecurity logic. A job queued in the browser is run through the identical registered-scope resolution, authorization gate, execution policy, sandbox, rate limit, retention and redacted audit trail as the command line — so it is indistinguishable, by policy and by audit, from a CLI job (ROADMAP WEB-A).

There is no POST /run-command and no arbitrary shell. The browser only submits a typed request — scanner, target, target_kind, scope_id — that the server validates with the same JobSubmission contract the API uses and translates into the same scope- and policy-gated ThemisJobStore.submit.

Running it

export OLYMPUS_THEMIS_API_KEY="$(head -c 48 /dev/urandom | base64)"   # ≥ 32 chars
olympus themis web --scope-directory .olympus/scopes --database .olympus/themis-jobs.sqlite3

For a live-capable deployment, enable the signed-authorization gate and use the same store and key for the API, Web and workers:

olympus themis web --scope-directory .olympus/scopes \
  --engagement-storage .olympus/engagements \
  --manifest-public-key approver-ed25519-public.pem

With --manifest-public-key, the New assessment form requires the complete signed JSON document. Preview and launch independently verify Ed25519 signature, digest, revocation, validity window, engagement id, target and scanner. Launch persists the exact document for worker-time revalidation and binds its SHA-256 digest to the job. A missing, malformed, expired, revoked, out-of-scope or wrong-technique manifest is rejected before queueing. Supplying a manifest to a server without a pinned key is also rejected. Without this option the legacy boolean-confirmation mode may still queue offline work for compatibility, but a live worker refuses every job without a bound manifest before the scanner application. It therefore cannot become live traffic by enabling the worker.

The web plane shares its command surface with olympus themis api:

  • Loopback by default. A non-loopback --host requires both --ssl-certfile

and --ssl-keyfile; the session cookie is Secure, so it is only sent back over HTTPS (browsers treat http://localhost as a secure context).

  • Credentials never on the command line. They come from

OLYMPUS_THEMIS_API_KEY or an identity register passed with --identities (scoped, revocable, expiring credentials — see themis-api-identities.md).

  • Same durable store. --database and --scope-directory point at the same

SQLite job store and registered scopes the CLI and API use.

  • Signed authorization. --manifest-public-key plus

--engagement-storage enables the same signed-manifest gate as the API and provides the retained document/revocation state used by workers.

  • Optional findings review. --findings-directory points at a folder of

core.Finding JSON bundles — the same read-only producer artifacts olympus vulcan findings consumes — and enables the Findings pages; --findings-storage points at the append-only lifecycle store so triage decisions made in the browser are recorded (and audited) there.

  • Optional scan diff. --baseline-directory points at a folder of

core.Finding bundles from an earlier run and enables the Scan diff page, which compares that baseline against the current findings.

Authentication and session

Login exchanges a valid Themis API credential for a short-lived, HMAC-signed session cookie (olympus_session). The cookie is:

  • HttpOnly — unreadable from JavaScript;
  • Secure — never sent over plain HTTP;
  • SameSite=Strict — not attached to cross-site requests.

The signing secret is generated per process, so restarting the server invalidates every session. Revocation and expiry of the underlying identity take effect immediately: each request re-resolves the identity from the register, so a revoked credential cannot ride an already-issued cookie.

CSRF, headers and Content-Security-Policy

Every state-changing form (/jobs, /jobs/{id}/cancel) carries a synchroniser CSRF token bound to the session nonce and checked in constant time. Combined with SameSite=Strict, a cross-site page cannot forge a submission.

Responses set a restrictive Content-Security-Policy with no inline script or style —

default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self';
connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'

— plus X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer and Cache-Control: no-store. The one stylesheet and the one progressive-enhancement script are same-origin static files, so the policy needs no 'unsafe-inline'. The request body is bounded to 64 KiB exactly as on the API.

Findings (WEB-C)

GET /findings surfaces the findings/verification end of the cycle in the browser, so an operator no longer has to drop to the terminal to review results. It is a faithful projection of the same interface-agnostic building blocks the CLI uses — no security or presentation logic is re-implemented in the page:

  • Source. Findings are loaded from --findings-directory with the identical

strict, bounded load_findings the CLI uses. The bundles are read-only producer artifacts; the page never rewrites them.

  • List and filter. The filter form reuses vulcan.search.FindingFilter

(status, minimum severity, source, engagement, exact asset, tags, CISA KEV, has-CVE, free text, minimum risk) and the result is ranked by vulcan.view.rank_by_risk, so the browser produces the same set an operator gets from olympus vulcan findings list — tags use AND semantics like the CLI --tag.

  • Detail. The detail cells come from FindingView.display_items, honest

about absence (a datum the finding does not carry renders as —, never a fabricated 0). The evidence table comes from vulcan.evidence_view.build_finding_evidence_view; with no custody ledger wired in, a structured reference is shown honestly as no-custody rather than disappearing, and inline snippets are redacted (SEC-H).

  • Lifecycle. The transition choices are exactly

core.finding_lifecycle.allowed_transitions of the finding's current status — the page cannot invent an illegal workflow edge. Recording a transition writes an immutable olympus.finding-transition record to the append-only --findings-storage store (who/when/from→to/why), and the effective status of a finding is folded from that history over the bundle's base status, so a decision made here is reflected everywhere the finding is shown without touching the producer artifact. Accepting a risk or marking a false positive requires a non-empty reason, mirroring core.finding_lifecycle.suppress.

Without --findings-directory the pages state plainly that the feature is not configured; without --findings-storage findings are shown read-only. Both degrade honestly rather than pretending there are no findings.

Apollo detection workbench (WEB-3 / API-2)

Start API or Web with --apollo-rules <directory> to expose a server-owned Apollo rule pack. Callers never choose filesystem paths or upload executable rules. GET /api/v1/apollo/rules returns the versioned olympus.apollo-rule-list contract; POST /api/v1/apollo/evaluate accepts 1–500 normalized olympus.event documents and returns olympus.apollo-evaluation 1.0.0. The Web page uses the same strict rule loader and evaluator. Evaluation is offline and bounded, performs no collection or network access, and remains attributed by the existing request audit trail.

Minerva custody-ledger verification (WEB-3 / API-2 / INT-3)

Both surfaces expose Minerva's chain-of-custody integrity check over the same I/O-free engine (olympus.minerva.custody.inspect_ledger_text, shared with the file-based CLI olympus minerva verify). POST /api/v1/minerva/verify-ledger takes an olympus.custody ledger as a JSON object and returns the versioned olympus.minerva-ledger-verification 1.0.0 contract: the ledger schema version, entry count, whether evidence is anchored, whether the ledger is signed, whether the signature was verified, the algorithm, and a normalized projection of the verified entries. The Web page GET /minerva accepts the same ledger pasted into a form and POST /minerva/verify renders the result. Both require minerva:read.

The hash chain is always verified: a successful response means it held, and a truncation, an inserted or reordered entry, or any edit to a sealed record is rejected with HTTP 422. The signature is verified only when the server is started with --minerva-custody-public-key <file> (a hex-encoded Ed25519 public key, not a secret) and the ledger is Ed25519-signed; without the key a signed ledger is reported signature_verified: false so a caller refuses to trust it. No key, filesystem path or evidence payload is ever accepted from the caller; the body is bounded by the existing 64 KiB request limit and verification is offline.

Metis CTI extraction workbench (WEB-3 / API-2)

POST /api/v1/metis/extract accepts a bounded raw body and a source_format (text, stix or misp) and returns the versioned olympus.metis-extraction 1.0.0 contract: the normalized indicators plus every element deliberately not imported, each with a reason. The Web page /metis uses the identical olympus.metis.extraction.extract_from_source core, so the browser, the API and the CLI case ingest agree on what each input yields. Free text runs the refanging, deduplicating IOC extractor; stix parses a STIX 2.1 bundle; misp parses a MISP event. Both surfaces require the metis:read scope, are CSRF- and rate-limited on the Web, and are bounded in input size and parsed-item count. Extraction is local and deterministic: no collection, enrichment or network access is performed, and an empty indicator set never implies the input was clean when elements were skipped.

Athena assessment planner (WEB-3 / API-2)

GET /api/v1/athena/profiles returns the versioned olympus.athena-profile-list 1.0.0 contract: the named, target-free scan profiles (light passive, deep active) with the registered adapters each one runs and whether it probes a target actively. POST /api/v1/athena/plan turns a profile plus an authorized target, an engagement scope and a confirmed authorization reference into the versioned olympus.athena-plan 1.0.0 contract: the resolved adapters, the embedded scope, the plan and scope SHA-256 digests, and the full canonical plan document ready to run with olympus athena run. The Web page /athena uses the identical olympus.athena core (ScanProfile.build_plan), so the browser, the API and the CLI (athena plan from-profile) produce byte-identical plans. Both surfaces require the athena:read scope and are CSRF- and rate-limited on the Web, with bounded target and domain counts.

Plan-building is a pure, deterministic, network-free computation: it produces a signable plan document, it never executes a scan. A profile never self-authorizes a run — the authorization must be confirmed explicitly (confirmed=true on the API, the confirmation checkbox on the Web) — so an unconfirmed or out-of-shape request is rejected with 422 rather than yielding a silently runnable plan.

Argus Certificate Transparency workbench (WEB-3 / API-2)

POST /api/v1/argus/ct-subdomains accepts a domain and the exact crt.sh JSON array (?output=json) and returns the versioned olympus.argus-ct-subdomains 1.0.0 contract: the in-domain subdomains, normalized, deduplicated and sorted. The Web page /argus uses the identical olympus.argus.ct.parse_crtsh_response core, so the browser, the API and olympus argus ct agree on what a given export yields. Only names that are a subdomain of the supplied domain and are conservative ASCII DNS hostnames are kept; a wildcard prefix (*.) is normalized away. Parsing is local and offline: no Certificate Transparency query is issued from the server — the caller supplies a response they already fetched. Both surfaces require the argus:read scope, are CSRF-protected on the Web and bounded in payload size. A payload that is not a JSON array is rejected with 422.

Artemis response-fingerprint workbench (WEB-3 / API-2)

POST /api/v1/artemis/fingerprint accepts a captured HTTP response (URL label, status, headers and an optional body) and returns the versioned olympus.artemis-fingerprint 1.0.0 contract: the detected technologies (product, category, optional version and the matched evidence). The Web page /artemis uses the identical olympus.artemis.fingerprint.fingerprint_response core, so the browser, the API and the Artemis scanner match a response the same way. Fingerprinting is a passive match against a curated signature set: no request is ever sent from the server, so the result reflects only the submitted headers and body. Both surfaces require the artemis:read scope, are CSRF-protected on the Web and bounded in header count and body size. An out-of-range status code or a malformed header line is rejected with 422.

Helios, Hermes and Proteus API slices (API-2)

These three ecosystem tools now expose a typed, versioned, passive and offline API slice, so every module is reachable over the same contract surface as the others. Each matches a captured artefact or validates submitted metadata locally; no network request, scan or email is ever made from the server. Each also has a dedicated Web workbench (/helios, /hermes, /proteus) that drives the same offline core from the browser, scope-gated and CSRF-protected (WEB-3), so every ecosystem tool now has both an API slice and a Web page.

  • Helios — POST /api/v1/helios/identify-service (scope helios:read,

contract olympus.helios-service-identification 1.0.0). The caller supplies a captured service banner and/or a port; the server sanitises the banner and matches it with the same olympus.helios.scanner core as the scanner. A volunteered banner is the only evidence; a port is a convention, used only as a fallback, and the result says which was used (identified_from: banner / port / none). An unknown banner is reported honestly, never upgraded into a claim. An empty request (no banner and no port) is 422.

  • Hermes — POST /api/v1/hermes/scan-text (scope hermes:read, contract

olympus.hermes-secret-scan 1.0.0). Scans submitted text for secrets with the same scan_text core as the CLI; every finding's value is masked before it leaves the server — a raw secret is never echoed back — and carries a stable fingerprint for de-duplication.

  • Proteus — POST /api/v1/proteus/validate-campaign (scope proteus:read,

contract olympus.proteus-campaign-validation 1.0.0). Validates and normalises non-target awareness-campaign metadata (header hygiene, a normalised sender address, a bounded landing URL) with the same core as the campaign builder, before any authorization or scope access. No email is sent; invalid input is 422 with the reason.

Knowledge views: correlations and explainability (WEB-8 / CORR-2 / EXPL-2)

Two pages surface the knowledge contracts in the browser, each on the same offline core as its CLI command and API endpoint — no scan and no network access, so the Web can never diverge from the CLI/API.

  • Correlations — GET /correlations renders the form; POST /correlations

(scope findings:read, CSRF-protected) takes a pasted JSON array of olympus.finding objects and derives the relationships between them with vulcan.correlate.correlations_document (the same olympus.correlations document as olympus vulcan correlate and POST /api/v1/vulcan/correlate). Every correlation is shown with its epistemic class — deterministic_result (a provable join), suggested_correlation (a lead), unverified_hypothesis (an inference to review) — and a banner states a correlation is a relationship, not proof of compromise. This is the WEB-8 honesty invariant: no view shows a hypothetical correlation as a proven fact. Malformed, wrong-shaped or over-limit input is 422.

  • Explain — GET /explain renders the form; POST /explain (scope

findings:read, CSRF-protected) takes a single olympus.finding object and renders vulcan.explain.explain_finding (the same olympus.finding-explanation contract as olympus vulcan explain and POST /api/v1/vulcan/explain): the risk factors, each claim tagged by its epistemic class (an inference is never shown as an observation), and the explanation's own limits. Derived only from the finding's fields — nothing fetched or invented.

These close the "Web view" remaining work of CORR-2 and EXPL-2. The broader cross-module UX of WEB-8 (contextual dashboards, shared visual language) builds on the same views.

Report export (WEB-I)

The findings view offers a one-click Vulcan report of exactly what is on screen. GET /findings/report takes the same filter query parameters as GET /findings (status, severity, source, text, KEV, has-CVE, min-risk, engagement, asset, tag) plus format (md, html, json, csv, sarif or pdf) and report_section (full or executive, applied to md/html only), narrows the catalogue with the identical vulcan.search.FindingFilter (so the report is exactly the filtered table), builds the canonical SecurityReport with vulcan.report.build_report_model, and renders it with the existing render_report_markdown / render_report_html / render_report_csv / the model's JSON dump — no rendering logic is duplicated in the web layer, so a report from the browser is byte-for-byte what the CLI produces for the same finding set. With report_section=executive the Markdown/HTML renderers emit a decision-maker summary — counts, severity table and a one-line-per-finding overview — omitting the per-finding detail, asset inventory, alerts and provenance appendix (the same --section executive the CLI offers; machine formats stay full). The csv format emits one spreadsheet-safe row per ranked finding (text/csv); every cell is neutralised against CSV formula injection, so an attacker-controlled finding field such as =HYPERLINK(...) is shown as literal text rather than executed by a spreadsheet. The sarif format emits SARIF 2.1.0 (application/sarif+json) of the filtered findings via the shared vulcan.sarif.findings_to_sarif, so the browser feeds the same interoperability format as olympus vulcan sarif-export. The pdf format renders a formatted PDF (application/pdf) via the shared vulcan.pdf.render_report_pdf; it needs the optional report extra (reportlab) and the endpoint returns 503 when that extra is not installed rather than serving a broken file. The response is a download (Content-Disposition: attachment), so what reaches the browser is a report, not a page. When set, engagement both filters the findings to that engagement and labels the report; it is sanitised (SEC-H) and slugified for the filename. tag is a comma-separated list with AND semantics, exactly like the CLI olympus vulcan findings list --tag. PDF stays CLI-only for now (olympus vulcan report --pdf, optional report extra); trends and notifications are the remaining WEB-I slices.

Scan diff (WEB-I)

GET /findings/diff compares a baseline run against the current findings and classifies every logical issue as new (a regression, or newly discovered), resolved (the evidence a remediation landed) or persistent (still open, with any severity/risk change shown). It reuses vulcan.compare.diff_findings — the same engine as olympus vulcan diff — so the browser and CLI agree, and matches findings by logical identity (same asset + same vulnerability), never by the per-run id. Both inputs are read-only producer artifacts: the baseline is --baseline-directory, the current set is --findings-directory. Without a baseline the page says plainly that the feature is not configured. GET /findings/diff?format=json returns the same ScanDiff projection as olympus vulcan diff --format json, for automation and CI regression gates.

New assessment (WEB-E)

GET /assessments/new is a guided, activity-first wizard for an operator who does not remember the CLI flags. It walks one path:

  1. Engagement (optional) → target and target kind → **registered

scope**.

  1. Activity — Reconnaissance, Network, Web application or

Vulnerability assessment. These are the activities that run as a Themis scanner job; Secret scan, Detection engineering and Full assessment are listed honestly as living in other modules (with their CLI command) rather than faked here.

  1. Tool — Automatic (Olympus picks a ready tool for the activity) or a

specific scanner. Each tool shows a plain-language summary and its risk badge; a catalogued-but-not-ready tool is shown disabled, never as runnable.

  1. Preview (POST /assessments/preview) — an "Olympus is about to run"

screen that re-validates the scope and engagement, resolves the scanner (honouring automatic mode), and states the risk class:

  • PASSIVE — observes public information, little or no traffic to the target;
  • ACTIVE — sends requests directly to enumerate and probe, non-destructive;
  • INTRUSIVE — attempts injection/exploitation, authorization mandatory.

Nothing is queued by previewing.

  1. Authorize and launch — the preview's launch form posts to POST /jobs.

Documented authorization is always required (the GUI cannot weaken the CLI's gate); for an ACTIVE or INTRUSIVE operation the preview adds a prominent warning naming the target.

The classification itself carries no GUI logic: the activity type is derived from each scanner's registry category and the risk class from a single reviewed map in olympus.integrations.activity (an unmapped scanner defaults to ACTIVE, never PASSIVE), so the web, and any future CLI/TUI wizard, read the same answers. Automatic mode refuses honestly when no scanner for the activity is ready on the host rather than queueing a job that cannot run.

Progressive enhancement only: the wizard works without JavaScript (every option is present and the server re-validates the activity/tool pairing on preview); a same-origin assessment.js simply filters the tool list to the chosen activity and shows the live hint.

Smart Scan (WEB-F)

GET /assessments/smart turns a goal — an objective, a target and (optionally) an engagement — into an ordered pipeline the operator reads before anything runs. It only proposes: POST /assessments/smart/plan queues nothing, runs no scanner and contacts no target. Each proposed step is a form that hands off to the normal POST /assessments/preview, so launching a step still passes the real scope gate, authorization check and risk preview — the Smart Scan page never weakens that gate.

An objective expands to a reviewed, ordered list of native activities (reconnaissance always first, so louder stages act on a mapped surface):

  • recon — reconnaissance only;
  • web-app — recon → web application → vulnerability assessment;
  • network — recon → network → vulnerability assessment;
  • full — recon → network → web → vulnerability assessment.

The proposal is:

  • deterministic and reproducible — the plan shows a stable SHA-256 digest

of its inputs and ordered steps; the same inputs always produce the same plan;

  • scope-aware — with an engagement chosen, a target outside its authorized

perimeter yields a plan with no steps (no branch is ever proposed out of scope);

  • policy-aware — a risk ceiling (default Active) drops any tool louder

than the ceiling with an explicit reason; Intrusive techniques appear only when the operator selects the Intrusive ceiling explicitly;

  • bounded and honest — only tools that are ready on this host are proposed,

and every dropped activity is listed with a reason rather than hidden.

The engine is the interface-agnostic olympus.integrations.smartscan (propose_pipeline), the same one the CLI olympus themis smart-scan uses, so the web and the command line propose identically. Progressive enhancement only: a same-origin smart_scan.js mirrors the chosen objective's summary into a hint.

Advanced mode (WEB-7)

GET /advanced (scope capabilities:read) is a dense hub for expert operators — pentesters, analysts, Red/Blue Team — on the same backend and the same controls as the guided flow. It groups the expert entry points that already exist: analysis (correlations, explain, ATT&CK coverage, scan diff), execution (new assessment, jobs) and detection & CTI (Apollo, Metis, Minerva).

The page holds no security logic of its own: every entry links to an endpoint that is already scope-gated server-side, and the page only reads the session's scopes to show what the current identity may reach. A tool the identity lacks the scope for is listed but not linked, annotated with the scope it would require; following such a link anyway still returns 403 from that endpoint. The CLI remains complete and independent of this view.

Tools (WEB-D)

GET /tools renders one card per catalogued engine straight from the real capability inventory — the same olympus.integrations.capabilities.inventory() that backs olympus themis capabilities and GET /api/v1/capabilities. The GUI never hardcodes a tool list, so the page shows exactly what this host knows:

  • name, category and a plain-language purpose for each engine;
  • its deployment class (local OSS binary, containerised OSS service,

proprietary remote API) and licence;

  • the honest readiness state — Ready, No Olympus adapter,

Engine not installed or Not configured — and the separate adapted, installed/configured and runnable here facts;

  • the Olympus maturity stage (how far the project has validated the

integration) and the next step that would advance it;

  • the requirements still missing before the engine can run; allowlisted

plugins also show their package distribution and version as provenance.

Because readiness is computed by the capability system and only an adapted and available engine is Ready, a catalogued-but-unadapted scanner (for example an API engine without an Olympus adapter) can never appear runnable. The page makes no network request and executes no engine, so an engine's installed version is detected at run time, not catalogued, and is deliberately not shown. Plugin distribution metadata is informational and does not establish package signing or production readiness.

Engagements (WEB-B)

Started with --engagement-storage <dir>, the web control plane reads the same engagements.db as olympus engagement and the same engagements as the API — one store, one model, no per-interface notion of scope. The engagement pages are read-only here (engagements are created from the CLI). When the new-assessment form has an engagement selected, the server resolves it from that store and refuses — with the engagement's own covers() logic, the host taken from the typed target (a url target by its hostname) — any target outside the authorized perimeter before the job is queued. The identical check runs on POST /api/v1/jobs when a submission carries an engagement_id, so an engagement's scope is enforced the same way from the browser, the API and the command line.

The engagement page distinguishes an unconfigured store, a configured empty store and an unreadable store. The assessment and Smart Scan forms also warn when the configured engagement store cannot be read, because scope choices cannot then be verified. The dashboard and incident catalogue now distinguish unavailable from configured-empty state; WEB-B-01 remains open for manual browser review and any additional unavailable states found there.

Live job state (server-sent events)

The job detail page works without JavaScript — it renders the authoritative server-side state on each load. When JavaScript is available, a same-origin EventSource subscribes to /jobs/{id}/events and updates the state line as the job advances, reloading once to show the final detail when the job reaches a terminal state.

The stream reports the store's real lifecycle states: queued, running, succeeded, partial (nothing ran — a missing dependency or live scanning off), failed, timed_out, cancelled and policy_denied. Sub-phases the worker does not record (parsing, normalising) are not invented: an honest state never implies coverage that did not happen.

Hostile data from targets (SEC-H)

Everything a target can influence — a hostname, a scanner error — is stripped of terminal control bytes and of URL query secrets before rendering, and Jinja2 autoescaping defuses HTML. A banner carrying an ANSI escape or a <script> payload cannot rewrite the operator's terminal, forge a log line or execute in the browser.

Relationship to the legacy VAP web

olympus themis serve now launches the same authenticated, scope-gated native Web UI as olympus themis web. The legacy source remains an archive for the pending full SEC-A parity review; Olympus does not launch it or import it. See themis-runtime.md for native migration, workers, Docker deployment and rollback.

Apollo telemetry formats / Formati telemetria

The operational /apollo form accepts normalized Event NDJSON (default), HTTP access logs, Zeek JSON and Windows/Sysmon JSON. Select the format before submitting up to 500 physical lines. Existing offline parsers feed the same detection engine. Skipped records are listed by line number and reason, without echoing raw log snippets. Any skips mean incomplete input, even with no alerts. The typed evaluation API still accepts normalized events only.

Il modulo operativo /apollo accetta Event NDJSON normalizzato (predefinito), access log HTTP, Zeek JSON e Windows/Sysmon JSON. Selezionare il formato e inviare al massimo 500 righe fisiche. I parser offline esistenti alimentano lo stesso motore di detection. Gli scarti sono visibili con numero di riga e motivo, senza riportare estratti grezzi dei log. Uno scarto indica input incompleto anche in assenza di alert. L’API di valutazione continua ad accettare solo eventi normalizzati.
