FASE 3 — Correzione applicata: SEC-4.2 (valutare l'ultimo run, non «uno qualsiasi»)

Difetto (fedeltà fail-closed). audit() calcolava successful con any(run.conclusion == "success") tra i run dello stesso check sullo SHA. GitHub, invece, valuta un required-check in base al suo run più recente. Conseguenza: un check il cui ultimo run è failure ma con un run precedente success veniva dichiarato PASS dall'audit post-merge, mentre GitHub lo considera rosso — l'audit poteva certificare «tutto verde» uno SHA che GitHub avrebbe bloccato.

Correzione. Nuovo helper _latest_run(runs, source_id) che restituisce il run più recente per quel source (per started_at, tie-break id). successful e terminal_failure ora guardano solo il run più recente per (check, source). Un re-run fallito successivo prevale (→ non soddisfatto, terminale); un re-run riuscito successivo soddisfa il check. Nessun caso a run singolo cambia (i test preesistenti restano verdi), quindi è una correzione di fedeltà senza regressioni.

# prima — "uno qualsiasi dei run è verde" (ottimistico, diverge da GitHub):
source_success = {sid: any(run.conclusion == "success" and <match source> for run in matching) ...}
# dopo — "il run più recente per source è verde" (come GitHub, fail-closed):
source_latest  = {sid: _latest_run(matching, sid) for sid in required_sources}
source_success = {sid: (run is not None and run.get("conclusion") == "success") ...}

Ruff (check + format) ✅; mypy src (gate reale) ✅ (i 2 avvisi su scripts/audit_required_checks.py — yaml senza stub e _effective_rules — sono preesistenti e fuori dal gate src); Bandit ✅ (0 issue); pytest offline verde (riga finale, PYTEST_RC=0). FASE 7 — Correzione applicata: redazione segreti nelle evidenze Themis

Difetto (anti-leak, fail-closed). themis/base._evidence redige stdout/stderr degli scanner prima di salvarli come raw_evidence. La regex _SECRET_ASSIGNMENT usava \b + alternanza fissa di keyword e separatore [:=] nudo, divergendo dal predicato di sensibilità dell'audit (_sensitive_key, substring su nome normalizzato). Conseguenza: tre classi di segreto sopravvivevano nelle evidenze mentre redact_mapping le avrebbe redatte — (1) JSON quotato "api_key":"…"/"access_token":"…" (virgolette+due punti rompono il separatore); (2) nomi composti con termine sensibile non iniziale (aws_secret_access_key, refresh_token, client_secret) — \bsecret/\btoken falliscono dopo _; (3) crumb successivi di un header Cookie multi-valore.

Correzione. _evidence decide ora la sensibilità del nome con lo stesso predicato dell'audit: _sensitive_key è promosso ad API pubblica is_sensitive_key (unica fonte di verità, usata da redact_mapping, redact_arguments e dalle evidenze). La regex del nome è ancorata a inizio-segmento con look-behind (?<![\w.\-]), tollera le virgolette JSON e consuma ancora uno schema di auth opzionale nel valore (Bearer <tok>). Un callback (_redact_assignment) redige il valore solo quando is_sensitive_key(nome) è vero.

Linearità (ReDoS). Il redattore scandisce l'intero output non fidato (fino a max_output_bytes, milioni di byte) prima del troncamento: una bozza con prefisso [\w.-]* + alternanza mostrava backtracking catastrofico (n=10k → hang). Il look-behind ancora ogni nome a un solo start per segmento → O(n) (4.5 MB ≈ 280 ms). Guardia di linearità aggiunta ai test.

Verifica. Ruff (check+format) ✅; mypy src ✅ (239 file); Bandit ✅ (0 issue); pytest offline verde (2956 passed, 9 skipped), inclusi property-test di sicurezza e mutation guardrail. Regressioni nuove in tests/unit/test_themis_execution.py (JSON quotato, nomi composti, cookie multipli, guardia di linearità); nessuna over-redazione dei campi non sensibili.

FASE 8 — Correzione applicata: redazione audit strutturato (URL nel testo libero)

Difetto (anti-leak, fail-closed). core/execution.redact_mapping redige i record di audit strutturati (StructuredAuditRecord.metadata, scritto da API/Web/jobs/CLI). Per i valori stringa _redact_value usava redact_url, che riscrive solo una stringa che è un URL. Un valore di metadata è però spesso una riga diagnostica di testo libero con un URL annidato (es. {"detail": "scanner fetched https://api/?api_key=SECRET during probe"}): redact_url lo lasciava invariato → segreto in chiaro nel record di audit. La stessa chiave sensibile sarebbe stata redatta, ma un segreto in un URL dentro una frase sotto chiave non-sensibile sfuggiva — lo stesso tipo di divergenza chiuso in FASE 7 sul lato evidenze.

Correzione. _redact_value usa ora redact_text per le stringhe: redige ogni URL trovato nel testo ed è un superset di redact_url per una stringa che è già un URL (nessuna sotto-redazione, i parametri non-segreto e il testo non-URL restano invariati). Il lato audit è così allineato al redattore delle evidenze Themis.

FASE 10 — Audit robustezza parser adapter + correzione (wapiti level → TypeError)

Metodo. run() (themis/base) cattura solo (ParseError, ValueError) dai parse() degli adapter: un'eccezione di altro tipo sfugge e fa crashare il run invece di fallire fail-closed (TOOLS-4.4). Harness di fuzzing su tutti i 16 adapter con output JSON/XML di forma errata (/tmp/.../scratchpad/fuzz_parsers.py): i parser sono risultati molto difensivi (isinstance/.get()/coercizione str()), nmap incapsula correttamente ET.ParseError. Un grep di int(/float( su valori non fidati ha isolato l'unico punto vulnerabile.

Difetto (fail-closed). wapiti.parse usava int(item.get("level", 1) or 1). Con un level di tipo lista/oggetto ({"vulnerabilities":{"XSS":[{"level":[1]}]}}), int([1]) solleva TypeError — non ValueError — che sfugge a run() → crash del worker. Verificato empiricamente. ("high" falliva l'intero scan via ValueError; i casi true/1.9 erano artefatti dell'harness con request=None.)

Correzione. Helper _level_value(raw): coerce a int solo per int/float/stringa numerica (bool escluso: un true JSON è spazzatura, non livello 1), altrimenti None → default INFO, come qualunque livello non riconosciuto. Coerente con lo stile lenient-per-campo del parser: un singolo campo malformato non annulla l'intero report né fa crashare il run; i livelli validi 1–4 restano LOW/MEDIUM/HIGH/CRITICAL.

Verifica. Ruff+format ✅; mypy src ✅ (239 file); Bandit ✅; pytest offline verde (3110 passed, 9 skipped), inclusi corpus-fuzz dei parser e grammar TOOLS-4.4. Regressioni in tests/unit/test_themis_output_grammar.py (level lista/oggetto/stringa/true/null → INFO senza crash; mapping dei livelli validi).

Esteso l'audit di robustezza oltre gli adapter a tutti i parser di input esterno/non fidato: CTI (metis/stix.py, misp.py — risultati solidi, rifiutano i valori non-stringa), ingest detection (apollo/ingest.py — _zeek_timestamp/_windows_event_id ben protetti), regole Sigma (apollo/sigma.py — int() solo dietro regex). Difetto (fail-closed). themis/legacy_vap._scan_inventory importa uno SQLite legacy esterno. Leggeva int(row["id"]): SQLite è tipizzato dinamicamente, quindi un DB ostile può contenere id NULL (→TypeError), testo/blob non numerico (→ValueError) o float anche con la colonna presente. Quelle eccezioni sfuggivano a LegacyVapSnapshotError (il try d'import cattura solo sqlite3.DatabaseError, poi except BaseException rilancia grezzo) → crash dell'import invece di errore di dominio fail-closed. Correzione. Helper _legacy_scan_id(raw): accetta solo int o stringa numerica (bool escluso), altrimenti LegacyVapSnapshotError("legacy scan id is not an integer"). Usato una sola volta per id (anche nella migration_key); dati validi invariati. Il rollback degli artefatti di snapshot nuovi vale come per ogni altra riga invalida.

Verifica. Ruff+format ✅; mypy src ✅ (239 file); Bandit ✅; pytest offline verde (3114 passed, 9 skipped). FASE 12 — Audit correttezza + correzione (hermes: provenienza segreti in file eliminati)

Metodo. Esaurito il tema crash su input esterno (harness su apollo-ingest/STIX/MISP/hermes loader: nessun escape; validate_contract_header/ContractVersion.parse e le regex STIX ReDoS-safe tutte solide), ho spostato la lente sulla correttezza del diff-parser del secret-scanner Git (hermes/scanner._scan_git_patch), dove un errore di provenienza ha valore di sicurezza (triage di una credenziale trapelata).

Difetto (correttezza/provenienza). Il percorso del file era ricavato solo da +++ b/<path>. Per un file eliminato l'header è +++ /dev/null, quindi current_path restava quello del file precedente del diff: un segreto nelle righe - di un file eliminato era attribuito al file sbagliato, con fingerprint_scope errato (dedup/baseline). Riprodotto: un segreto in secrets.env (eliminato) risultava in keep.txt. Nessun falso negativo (il segreto è comunque rilevato), ma provenienza fuorviante.

Correzione. Il parser traccia old_path (da --- a/<path>) e new_path separatamente; ogni riga - è attribuita al vecchio file, ogni riga + al nuovo — corretto anche per i rename. File modificati invariati; i fingerprint cambiano solo nei casi prima mal-attribuiti (eliminati/rinominati).

Verifica. Ruff+format ✅; mypy src ✅ (239 file); pytest offline verde (3115 passed, 9 skipped). Regressione in tests/unit/test_hermes.py (segreto in file eliminato → attribuito a secrets.env, non a keep.txt). hermes/scanner non è nel mutation gate.
