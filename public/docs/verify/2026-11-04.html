Review AppSec del control plane Web/API — 2026-11-04

Audit mirato (AppSec + Red/Blue) delle superfici a più alto rischio di un tool di sicurezza professionale: l'API autenticata (themis/api.py) e il control plane Web (themis/web.py). Esito: nessuna vulnerabilità sfruttabile. Checklist verificata:

API (themis/api.py)

  • Authz per endpoint: ogni endpoint dati/azione dichiara una dipendenza di scope

(authenticated("<scope>")): autenticazione via header API-key o OIDC bearer, poi 403 se l'identità non ha lo scope richiesto. Scope distinti per capacità (capabilities:read, jobs:read/write/cancel, apollo:read/run, …).

  • Unico endpoint aperto: /health (stato/versione statici, nessun dato). /ready e

/metrics (Prometheus) sono dietro auth (reads_capabilities).

  • OIDC: bearer ostili sempre normalizzati a errore (property test esistente

test_themis_oidc), mai eccezione non gestita.

Web (themis/web.py)

  • Rendering: FastAPI Jinja2Templates con autoescape attivo; nessun | safe,

Markup o autoescape false nei template (solo <script src> statici, nessuna interpolazione di variabili in script) → XSS mitigato.

  • Sessione: cookie firmato, HttpOnly + Secure + SameSite=Strict, emesso solo da

una credenziale API valida; _require_session protegge le pagine.

  • CSRF: token sincronizzatore HMAC legato alla sessione, verificato in tempo costante

(hmac.compare_digest) su tutte le 11 route POST che cambiano stato; 403 su mismatch. Doppia difesa con SameSite=Strict.

  • Login: throttling anti-guessing prima di qualunque verifica; 401 su credenziale

errata.

Nessuna correzione necessaria. Osservazione minore (non vulnerabilità, non corretta): la POST /logout non verifica il token CSRF, ma SameSite=Strict impedisce comunque il POST cross-site; un «forced logout» è a basso impatto e il logout è spesso CSRF-exempt per scelta. Nessun endpoint dati risulta privo di autenticazione.

Review exploit-safety del confine scanner (subprocess + output non fidato) — 2026-11-04

Audit Red-team del confine più critico di una piattaforma di scanner: l'esecuzione degli engine esterni e il parsing del loro output (dati non fidati). Esito: nessuna vulnerabilità. Difese verificate:

  • Esecuzione: nessun shell=True, os.system, eval, exec, pickle.load né

yaml.load non sicuro in src; i subprocess usano solo la forma exec-con-argv (create_subprocess_exec / Popen con vettore fisso). L'argv degli engine governati deriva dall'allow-list del manifest (engines.argv, già auditato).

  • Output non fidato: cap su byte (max_output_bytes, default 5 MB, 1–100 MB,

applicato da un thread lettore → CommandOutputLimit) contro resource-exhaustion; limite di profondità nel parsing JSON (anti nesting-DoS); max_findings (anti memory-exhaustion); _safe_line tronca e sanitizza le stringhe derivate dallo scanner prima della visualizzazione (anti ANSI/terminal-injection).

  • XML: l'unico adapter che parsa XML (nmap) usa defusedxml (XXE ed espansione entità

disabilitate al confine del parser); gli altri usi di xml.sax.saxutils.escape sono output-escaping (graph/PDF), non parsing.

  • Copertura: i parser hanno contract test e fuzzing (INT-1, test_themis_parser_corpus_fuzz).

Nessuna correzione necessaria. Con la review Web/API precedente, le due superfici a più alto rischio del tool risultano auditate e solide in questa data.

Correzione accuratezza del gate preview --require-engine — 2026-11-04

Difetto (in una feature mergeata oggi): themis preview --require-engine controllava solo il binario su PATH, ignorando le dipendenze dati pinnate dell'engine. Per nuclei (che richiede nuclei-templates al commit pinnato) il gate diceva «pronto» anche con i template mancanti/sbagliati → falso positivo per un gate di automazione, incoerente col gate gemello engines preflight (che fa già la verifica completa).

  • Correzione: nuovo olympus.engines.preflight.scanner_readiness(env, scanner) — la

verifica completa (inspect_engine) scope-ata al singolo scanner (non pretende i mandatory), incl. versione/commit e data-deps. preview --require-engine lo usa: exit 8 con il motivo preciso (es. «nuclei-templates al commit sbagliato»). Il default (senza flag) resta il check leggero which, che non avvia processi; l'help del flag chiarisce che --require-engine esegue il probe di readiness.

  • Test: test_engine_preflight.py — scanner_readiness segnala DATA_PROBLEM quando la

data-dep è al commit sbagliato pur col binario presente, e None per uno scanner non governato. Aggiornato il test del preview al nuovo messaggio («not ready»).

  • Verifiche: Ruff, mypy --strict (234), cli-reference rigenerato, doc-links, suite

completa offline verde (PYTEST_EXIT=0). CHANGELOG aggiornato.
