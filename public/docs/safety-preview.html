Safety preview di un run pianificato

Prima che un singolo scanner parta, un operatore deve poter rispondere in un unico punto e in termini chiari alla domanda: "cosa sto esattamente per fare?". Questo è lo scopo del safety preview (ROADMAP UX-B).

Modulo interface-agnostic: olympus.themis.preview. Comando: olympus themis preview.

Una sola fonte per tutte le interfacce

Il preview non contiene logica di sicurezza propria: riusa i primitivi già esistenti, esattamente come olympus.integrations.activity è l'unica fonte della classificazione di rischio.

InformazioneDa dove arriva
Esito scope (statico)olympus.themis.scope.ensure_allowed — nessuna attività di rete
Classe di rischio + spiegazioneolympus.integrations.activity (PASSIVE/ACTIVE/INTRUSIVE)
Tool esternoScannerSpec.binary (o marcatore "remote API service")
Comando pianificato (argv redatto)adapter.build_argv offline, ogni token via redact_url + safe_terminal_text (SEC-G); None per scanner senza adapter nativo o target bloccato
Target normalizzato, budget, output, autorizzazioneil ThemisRunRequest pianificato

Così CLI, TUI e Web control plane mostrano lo stesso SafetyPreview (to_dict() serializzabile) invece di re-derivare ciascuna la propria risposta, e il "cosa sto per fare" non può divergere tra interfacce.

Strettamente offline: lo scope non risolve il DNS

Il controllo di scope è statico. ensure_allowed valida host/dominio/CIDR senza contattare nulla, e il preview non risolve mai nomi. Quando la decisione definitiva richiederebbe la risoluzione a run-time (per bloccare rebinding/SSRF contro l'indirizzo risolto), il preview lo dichiara onestamente invece di far credere che il nome sia già autorizzato.

Conferma proporzionata

Il preview espone requires_confirmation, il predicato che un'interfaccia usa per decidere se chiedere una conferma esplicita (UX-B):

  • run active o intrusive non simulati → conferma richiesta;
  • run passive o in --simulate → nessuna conferma aggiuntiva.

Uno scanner non riconosciuto non è mai sottostimato: default a ACTIVE, scanner_known=False, e quindi conferma richiesta.

Uso da riga di comando

Il comando non esegue nulla e non contatta alcun target: è una lettura offline, scriptabile, da fare prima di accodare o lanciare un job.

# Riepilogo umano
olympus themis preview nmap --target 10.0.0.5 --scope scope.json --i-am-authorized

# Output machine-readable per la CI
olympus themis preview sqlmap --target app.example.com --kind url \
  --scope scope.json --i-am-authorized --format json

I campi derivati dal target passano per safe_terminal_text, così un hostname ostile non può falsificare righe o iniettare sequenze di escape nel terminale dell'operatore (SEC-H).

Codici di uscita

CodiceCausa
0Preview prodotto; lo scope non blocca il lancio (in_scope o resolution_required).
2Uso errato: --kind/--format non validi, scope file assente o non valido.
3Lo scope bloccherebbe il lancio (out_of_scope, blocked o target invalid).

Il codice 3 è un esito onesto, non un errore del preview: permette a uno script di ramificare senza interpretare il testo.

Dopo il run: esito onesto e distinto

La controparte post-esecuzione del preview è il summary dell'esito (UX-B): un run concluso può trovarsi in stati che a colpo d'occhio si somigliano ma significano cose molto diverse, e tutti portano zero finding reali — simulato, scanner non disponibile, disabilitato, fallito, annullato o parziale — esattamente come un run che è davvero arrivato in fondo senza trovare nulla. Confonderli è pericoloso: un parziale non deve mai sembrare "nessuna vulnerabilità".

Modulo interface-agnostic: olympus.themis.outcome. Fonte unica anche qui, così CLI, TUI e Web mostrano lo stesso verdetto.

La proprietà di sicurezza è un solo predicato: trustworthy_empty è vero solo per clean. Ogni altro stato è conclusive=False: l'assenza di finding non dice nulla sull'esposizione del target.

# Riepilogo umano dell'esito di un job concluso
olympus themis jobs status THEMIS-<id> --format table

Il formato predefinito di jobs status resta json (contratto completo, invariato). Il summary è fail-safe: uno stato persistito sconosciuto è trattato come failed, mai come pulito.

Cosa resta da fare

Questa è la fonte dati (preview pre-run + summary dell'esito) e la sua esposizione CLI. L'innesto nel rendering della TUI e nella Web UI, la conferma interattiva in-flow e il kill switch sempre visibile restano follow-up tracciati in ROADMAP.md sotto UX-B.
