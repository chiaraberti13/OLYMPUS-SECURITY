Themis scanner isolation

A scanner is untrusted code processing untrusted remote output. Themis therefore never runs one as "just another subprocess": every child started by olympus.themis.runner.run_command is confined by the policy in olympus.themis.sandbox before it reaches exec, and every child that stops is described by a structured reason rather than a bare exit status.

Implemented in src/olympus/themis/sandbox.py and src/olympus/themis/runner.py; tested in tests/unit/test_themis_sandbox.py against the real kernel behaviour (real setrlimit violations, a real ignored SIGTERM, a real process group).

Isolated scratch spaceFresh 0700 directory used as the child's cwd, TMPDIR, TMP, TEMP and HOME, removed when the run ends
Bounded outputIncremental capped reads of stdout/stderr (max_output_bytes)
Whole-tree terminationOwn session and process group; SIGTERM to the group, then SIGKILL after the grace window
Explainable outcomeA TerminationReport recorded on the result document

Privileges are dropped before the limits are applied: setuid is itself subject to RLIMIT_NPROC, and lowering a limit afterwards needs no privilege. The drop, the umask and the new session are done by subprocess in C, so no Python runs between fork and the privilege drop; the only post-fork Python is the setrlimit loop, which has no Popen parameter.

Running as root is refused, not assumed

When the parent process is root, the child drops to THEMIS_SANDBOX_USER (nobody by default). If that account does not exist — or resolves to uid 0 — the run is refused with TerminationCause.SANDBOX_DENIED and nothing is executed. Accepting the risk is explicit and auditable:

THEMIS_SANDBOX_ALLOW_ROOT=true olympus themis run ...

When the parent is already unprivileged, no drop is attempted and the scanner inherits that account.

Termination causes

TerminationReport.cause is one of:

CauseMeaning
completedThe process set its own exit status
timeoutThe per-command timeout elapsed; the group was terminated
cancelledThe caller requested cooperative cancellation
output_limitCombined stdout/stderr passed max_output_bytes
resource_limitThe kernel enforced a limit (SIGXCPU → cpu_seconds, SIGXFSZ → file_size_bytes)
signalledThe process died from a signal Olympus did not send
start_failedMissing binary, invalid argv, or a failed exec
sandbox_deniedThe required isolation could not be established; nothing ran

The report also records escalated_to_kill (the scanner ignored SIGTERM), process_group_signalled (the whole group was signalled, not just the leader), the limit that was crossed, the signal name, and the unprivileged account used. It is persisted as the optional termination object of the olympus.themis-result contract. Schema 1.2.0 also carries optional job_id and manifest_sha256 authorization provenance; consumers pinned to 1.1.0 must negotiate or upgrade before accepting the newer document.

Schema 1.3.0 adds partial and partial_reason (the engine ran but covered less than requested, e.g. output records it could not parse). It is emitted only for a partial result; every other result is still written as 1.2.0 with no new keys, so readers pinned to 1.2.0 keep working and only need to upgrade to read a partial document. A partial live result exits 5, becomes a partial job and is never reported as a clean empty.

Note that CPython ignores SIGXFSZ and surfaces EFBIG instead, so a Python-based scanner that crosses file_size_bytes fails with a write error rather than a signal. The limit holds either way; only the recorded cause differs.

Memory limit and Go engines

THEMIS_SANDBOX_MEMORY_BYTES (default 2 GiB) is applied as RLIMIT_AS, a limit on address space, not on resident memory. Go programs reserve far more address space than they use, so an engine that needs under 1 GB of RAM can still be refused by a 2 GiB limit. Measured with the pinned nuclei v3.11.1 and the full pinned template set (14,104 templates), run through this sandbox against a loopback server:

THEMIS_SANDBOX_MEMORY_BYTESResult
2 GiB (default)fatal error: out of memory within ~5 s, exit 2 (reported as failed, never clean)
4 GiBcompletes: live, not partial, ~420 s
8 GiBcompletes: live, not partial, ~415 s

The requirement is recorded in the engine manifest ([adapter].min_memory_bytes); olympus engines doctor notes when the host limit is below it, and the failure message names the variable. Olympus never raises the limit by itself: the scanner image sets 4 GiB because it ships nuclei with the full templates, and a host running a smaller template set can keep the default.

What this layer deliberately does not do

Live execution is additionally fail-closed at the application boundary. Before scope resolution or adapter construction, Olympus verifies a root-owned OCI runtime marker, a pinned image-attestation digest, read-only /, zero effective capabilities, NoNewPrivs=1 and active seccomp filter mode from /proc. These properties cannot be enabled by a CLI flag or environment variable. Direct host themis run, workers and jobs work invocations may still simulate or process disabled work, but cannot start a live scanner.

The following remain open on the hardening roadmap. Do not read the guarantees above as covering them:

  • Egress allowlisting for scanner processes. DNS rebinding is closed inside

Olympus by address pinning (olympus.core.pinning), but an external scanner binary resolves and connects on its own; only a network policy can bound where it goes.

Compose does separate the planes: API and Web are attached only to the internal control network, while the worker and optional engines are attached only to scan-egress; migration has no network and no service is dual-homed. The shared SQLite volume transfers jobs without opening a control-plane network path. This topology is a boundary, not an egress allowlist: scan-egress remains externally routable until a per-job policy restricts it to validated scope addresses and ports.

The container test starts the native runtime under the repository profile and probes a denied process_vm_readv call. It also runs a bounded, offline escape probe with a 32-PID cgroup limit: the probe checks the read-only root, writable scratch, absence of a host-only canary, protected kernel memory, zero effective capabilities, no-new-privileges, seccomp filter mode and denied user-namespace creation. A real child that ignores SIGTERM is also run through the production runner with a 0.5-second timeout and grace period: the probe requires signalling the whole process group, SIGKILL escalation, a structured timeout report and a 10-second outer deadline. All spawned children are reaped even on failure. This demonstrates profile loading, mandatory live-runtime attestation and selected kernel controls in CI; it does not demonstrate egress containment or close SEC-B by itself.

Optional AppArmor enforcement

On Linux hosts with AppArmor enabled, load the repository policy before starting the worker overlay:

python scripts/manage_scanner_apparmor.py status
sudo python scripts/manage_scanner_apparmor.py install
docker compose -f docker-compose.yml -f docker-compose.apparmor.yml up --build

The provisioner validates the policy identity, version, regular-file type and digest, never invokes a shell, and loads it idempotently with apparmor_parser -r -W. It fails without AppArmor, the parser or root privileges and never installs packages implicitly. Preserve its JSON output as deployment evidence; the container test then verifies both the effective profile and the denied canary.

The profile is named olympus-themis-scanner, remains in enforce mode and complements rather than replaces the read-only root, dropped capabilities, no-new-privileges and seccomp controls. Do not silently fall back to apparmor=unconfined; omit the overlay only on a host where AppArmor is not an available LSM and record the residual risk.

Operational notes

  • cwd defaults to the run's private scratch directory. A caller that passes

its own cwd is responsible for making it reachable by the unprivileged account.

  • The scratch directory is removed when the run ends, including after a timeout

or a kill. Anything a scanner must keep has to be written to the evidence path, not to TMPDIR.

  • RLIMIT_AS bounds address space, not resident memory. A runtime that

reserves large virtual mappings (JVM-based scanners, for example) may need THEMIS_SANDBOX_MEMORY_BYTES raised above the default.
