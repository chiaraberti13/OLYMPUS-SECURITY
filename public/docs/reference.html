English

What Olympus does

Olympus is a single command, olympus, behind which live 9 modules — 4 offensive (red), 3 defensive (blue), 2 for correlation/reporting — that would normally be 9 separate tools from 9 different projects, each with its own incompatible output format. Here they share the same data contract (core.Asset, core.Finding, core.Alert, core.Incident): an asset discovered by Argus can be verified by Helios, detected by Apollo, handled by Minerva, and end up in the same report generated by Vulcan — keeping the same ID (AST-2026-00001) the whole way through.

In short, here's the path data takes as it moves from one module to the next:

 domain / IP / URL / handle — always inside an authorized scope
        │
        ▼
  Argus · Helios · Artemis · Proteus     (🔴 red: discover and verify, never out of bounds)
        │  core.Asset + core.Finding (same ID)
        ▼
  Hermes · Apollo · Minerva              (🔵 blue: detect, correlate, keep custody of evidence)
        │  core.Alert + core.Incident
        ▼
       Vulcan                            (🟣 aggregates it all, dedupes, CVSS → pentest report)

You don't need to understand this diagram to start using Olympus — it's here only for the curious, to explain why the modules share data. In practice you'll run individual olympus <module> <command> commands, each explained one by one further down this guide.

This guide is written for someone who has never used Olympus before: it follows the order — install, first run, the complete command list, an options legend, a full guided walkthrough on a practice target included in the repo — so you can follow it start to finish without already knowing anything.

Warnings, responsibility and licence

Scope is mandatory, always. Every offensive module (Argus, Helios, Artemis, Proteus) requires a scope file (JSON) listing what you're authorized to test. Any target outside that list gets blocked and logged to an audit log — never silently ignored, never run anyway. Some commands also require the explicit --i-am-authorized flag before proceeding with a real lookup or an active test.

Non-destructive, always. No module runs real exploits, DoS, credential brute-forcing, or detection evasion. Helios only does TCP discovery; Artemis tests for XSS/CVEs only by presence (never a payload that actually exploits the flaw); Proteus never collects real credentials — anyone who clicks a phishing simulation only sees a training page. These are verification tools, not attack tools.

Requirements

  • Python 3.11 or newer, with pip.
  • An Internet connection only for the modules that do real lookups (Argus, Helios,

Install and first run (step by step)

This section walks you, one step at a time, from nothing to a first real command run successfully. No prior experience with Olympus is needed.

Step 1 — Download and install.

Open a terminal and paste:

First verify that Python 3.11 or newer is available (macOS commonly exposes it as python3, not python):

python3 --version

If that command is missing on macOS, install Python from python.org or with Homebrew (brew install python), then open a new terminal. Do not use the legacy system Python.

git clone https://github.com/chiaraberti13/olympus-security.git
cd olympus-security
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"

The venv is an isolated Python environment: everything you install stays inside the .venv folder, without touching the rest of your system. Every time you reopen a terminal in this folder, remember to reactivate it with source .venv/bin/activate (your terminal prompt shows (.venv) when it's active).

Step 2 — Verify the install.

olympus --version
olympus --help

The first prints the installed version; the second lists the 9 available modules. If instead you see command not found: olympus, the venv isn't active — repeat source .venv/bin/activate inside the olympus-security folder.

Step 3 — Your first real command (zero network, zero setup).

Hermes, the secret scanner, makes no network requests and needs no scope file at all: it's the fastest way to see Olympus do something real.

olympus hermes scan src --output /tmp/hermes-findings.json

Scans the source code for API keys, tokens and credentials accidentally left behind (known regex patterns + entropy-based detection). This repository comes back clean (0 potential secret(s)). The command exits with code 1 if it finds something (so you can chain it in a CI pipeline), 0 if it finds nothing — that's expected behaviour, not an error.

Step 4 — Understand scope, and run your first networked command.

Offensive modules never accept a "free-hand" target: they require a scope file, a JSON document explicitly listing what you're authorized to test. The repository ships one already set up for a synthetic demo domain:

cat examples/input/argus-scope.json
{
  "engagement": "olympus-demo-corp-2026",
  "allowed_domains": ["olympusdemocorp.example"]
}

Now try real passive DNS recon against that domain:

olympus argus scan --domain olympusdemocorp.example --scope examples/input/argus-scope.json

This really queries DNS, MX, SPF/DMARC, and exports the result to argus-assets.json in the current directory as a core.Asset (pass --output to write it elsewhere).

Step 5 — See what happens outside scope.

Now try a domain that is not listed in the scope file:

olympus argus scan --domain some-random-domain.com --scope examples/input/argus-scope.json

The command refuses to proceed, prints blocked, out of scope, and exits with code 3 — no network request is ever made toward that domain. The event is written to the audit log (~/.local/state/olympus/audit/argus-blocked.log by default — see Where Olympus writes): this is how every offensive module respects its perimeter, always, with no silent exceptions.

Step 6 — Aggregate everything into a report.

Each module writes its own JSON output as a wrapper document (e.g. {"assets": [...]}); Vulcan instead reads an array of core.Asset/Finding/Alert objects. Pull the array out with one line of Python, then hand it to Vulcan:

python -c "import json; json.dump(json.load(open('argus-assets.json'))['assets'], \
  open('/tmp/vulcan-assets.json', 'w'))"

olympus vulcan report --engagement "olympus-demo-corp-2026" \
  --assets /tmp/vulcan-assets.json \
  --output vulcan-report.json \
  --markdown vulcan-report.md \
  --html vulcan-report.html

Vulcan merges, deduplicates and produces one consolidated report. Open vulcan-report.html in a browser: it's a self-contained report (no external resources), ready to hand off.

From here you can explore the rest: the full command list below, or the complete guided walkthrough further down this guide, which uses a real practice target (included in the repo) to show the whole red→blue→report chain.

Canonical exit codes — the same across every module, so a CI pipeline can react to why a command stopped, not just to the fact that it did:

CodeMeaning
0all good: full coverage, nothing to report
1found something you may want to look at (a secret, a finding, an alert…)
2usage or input error (bad flag, unreadable or malformed file)
3blocked: the target is outside the authorized scope (and was logged)
4refused: an explicit authorization flag (--i-am-authorized) was required and missing
5partial: the run lost coverage, so its findings are not exhaustive
6failed: nothing completed, so the result carries no information
7cancelled: the run stopped on request before finishing
8engine missing: a mandatory external engine is absent, so nothing ran (no network was touched)

Codes 5 and 6 are what let a pipeline tell "we looked everywhere and found nothing" from "we could not look" — see run status and coverage.

Configuration file (optional) — to stop repeating the same flags, create olympus.toml in the folder you run commands from (or ~/.olympus.toml, or point $OLYMPUS_CONFIG at a path):

[http]
timeout = 15.0
retries = 3
rate = 0.25
backoff = 0.5
jitter = 0.2   # spread each retry wait by +/- this fraction (0 = off)

Where Olympus writes — two kinds of file, two different homes:

KindDefaultOverride
Reports and exports — what you asked for (--output, --markdown, --html, --pdf)a plain filename in the directory you ran the command from, e.g. argus-assets.json--output <path>
Audit and block logs — written implicitly when a target is refused (--log)~/.local/state/olympus/audit/, following $XDG_STATE_HOME when set--log <path>, or $OLYMPUS_STATE_DIR for all of them at once

Audit logs deliberately do not depend on your working directory: they are written as a side effect of a scope violation, so they must land in the same place whether you ran the command from your home directory or from a checkout. OLYMPUS_STATE_DIR is read once at startup.

Guided walkthrough: from recon to report, on a practice target included in the repo

The repository ships Mars, a deliberately vulnerable target that runs locally (127.0.0.1, synthetic data only): the right way to practise the real tools against something you're always authorized to test, without having to find an external domain.

# Start the target (in a separate terminal, leave it running)
python labs/mars/target/app.py        # http://127.0.0.1:8081

# In the other terminal, with the venv active:
S=labs/mars/target/practice-scope.json

olympus artemis fingerprint --url http://127.0.0.1:8081/ --scope $S
olympus artemis content --url http://127.0.0.1:8081/app \
  --wordlist examples/input/artemis-content-wordlist.txt --scope $S --i-am-authorized
olympus artemis xss --url "http://127.0.0.1:8081/app/search?q=x" --param q \
  --scope $S --i-am-authorized
olympus artemis metabase --url http://127.0.0.1:8081 --scope $S --i-am-authorized

# Then the blue side: detect a simulated post-exploitation chain (never a real capture)
olympus apollo run --rules examples/input/apollo-redteam \
  --events labs/mars/target/mars-post-exploitation.ndjson

The complete step-by-step guide, explaining every deliberate weakness of the target, is in labs/mars/README.md.

Troubleshooting

  • command not found: olympus — the venv isn't active. Run

source .venv/bin/activate inside the olympus-security folder.

  • ModuleNotFoundError or import errors — the install didn't complete, or was run outside

the venv. Repeat pip install -e ".[dev]" with the venv active.

  • blocked, out of scope (exit code 3) — expected behaviour, not a bug: the target isn't

in the file passed via --scope. Add it to the scope JSON if you really are authorized to test it.

  • refused: --i-am-authorized required (exit code 4) — the command performs a real

lookup against a third party or an active test: only re-run it with --i-am-authorized if you genuinely have documented authorization.

  • make check fails on the coverage gate — the dev dependencies are missing: make sure you

installed with pip install -e ".[dev]" (not just pip install -e .) and that the venv is active.

  • A command doing real lookups hangs or times out — check your connection, and double-check

the scope you passed actually includes the target: without network, the offline modules (Hermes, Apollo, Minerva) keep working normally.

  • Want to try Mars but don't have Docker — you don't need it:

python labs/mars/target/app.py starts the target without Docker, as shown above.

Uninstalling

deactivate            # exit the venv, if active
rm -rf .venv           # removes the isolated Python environment and every installed dependency
cd .. && rm -rf olympus-security   # removes the repository itself, if you no longer need it

Nothing outside the project folder is touched: no file is written anywhere else on the system.

Installazione e primo avvio (passo passo)

Questa sezione ti porta, un passo alla volta, da zero a un primo comando reale eseguito con successo. Non serve alcuna esperienza precedente con Olympus.

Passo 1 — Scarica e installa.

Apri un terminale e incolla:

Verifica prima che sia disponibile Python 3.11 o successivo (su macOS è normalmente esposto come python3, non come python):

python3 --version

Se su macOS anche questo comando non esiste, installa Python da python.org oppure con Homebrew (brew install python), quindi apri un nuovo terminale. Non usare il vecchio Python di sistema.

git clone https://github.com/chiaraberti13/olympus-security.git
cd olympus-security
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"

Il venv è un ambiente Python isolato: tutto quello che installi resta dentro la cartella .venv, senza toccare il resto del sistema. Ogni volta che riapri un terminale in questa cartella, ricordati di riattivarlo con source .venv/bin/activate (il prompt del terminale mostrerà (.venv) quando è attivo).

Passo 2 — Verifica l'installazione.

olympus --version
olympus --help

Il primo stampa la versione installata; il secondo elenca i 9 moduli disponibili. Se invece di questo vedi command not found: olympus, il venv non è attivo — ripeti source .venv/bin/activate dentro la cartella olympus-security.

Passo 3 — Il tuo primo comando reale (zero rete, zero configurazione).

Hermes, lo scanner di secret, non fa nessuna richiesta di rete e non ha bisogno di alcun file di scope: è il modo più veloce per vedere Olympus fare qualcosa di vero.

olympus hermes scan src --output /tmp/hermes-findings.json

Scansiona il codice sorgente alla ricerca di chiavi API, token e credenziali dimenticate (regex note + rilevamento tramite entropia). Su questo repository esce pulito (0 potential secret(s)). Il comando esce con codice 1 se trova qualcosa (così puoi incatenarlo in una pipeline CI), 0 se non trova nulla — non è un errore, è il funzionamento previsto.

Passo 4 — Capisci lo scope, ed esegui il tuo primo comando in rete.

I moduli offensivi non accettano mai un target "a mano libera": vogliono un file di scope, un JSON che elenca esplicitamente cosa sei autorizzato a testare. Il repository ne include uno già pronto per un dominio di dimostrazione sintetico:

cat examples/input/argus-scope.json
{
  "engagement": "olympus-demo-corp-2026",
  "allowed_domains": ["olympusdemocorp.example"]
}

Ora prova la ricognizione DNS passiva reale contro quel dominio:

olympus argus scan --domain olympusdemocorp.example --scope examples/input/argus-scope.json

Interroga davvero DNS, MX, SPF/DMARC ed esporta il risultato in argus-assets.json nella directory corrente come core.Asset (usa --output per scriverlo altrove).

Passo 5 — Guarda cosa succede fuori dallo scope.

Prova adesso un dominio non elencato nel file di scope:

olympus argus scan --domain un-dominio-a-caso.com --scope examples/input/argus-scope.json

Il comando si rifiuta di procedere, stampa blocked, out of scope ed esce con codice 3 — niente richiesta di rete viene mai fatta verso quel dominio. L'evento resta scritto nel log di audit (~/.local/state/olympus/audit/argus-blocked.log di default — vedi Dove scrive Olympus): è così che ogni modulo offensivo rispetta il perimetro, sempre, senza eccezioni silenziose.

Passo 6 — Aggrega tutto in un report.

Ogni modulo scrive il proprio output JSON come un documento avvolgente (es. {"assets": [...]}); Vulcan invece legge un array di oggetti core.Asset/Finding/ Alert. Estrai l'array con una riga di Python, poi passalo a Vulcan:

python -c "import json; json.dump(json.load(open('argus-assets.json'))['assets'], \
  open('/tmp/vulcan-assets.json', 'w'))"

olympus vulcan report --engagement "olympus-demo-corp-2026" \
  --assets /tmp/vulcan-assets.json \
  --output vulcan-report.json \
  --markdown vulcan-report.md \
  --html vulcan-report.html

Vulcan unisce, deduplica e produce un report unico. Apri vulcan-report.html in un browser: è un report autosufficiente (nessuna risorsa esterna), pronto da consegnare.

Da qui puoi esplorare il resto: l'elenco completo dei comandi qui sotto, oppure il percorso guidato completo più avanti in questa guida, che usa un bersaglio di prova reale (incluso nel repository) per mostrare l'intera catena red→blue→report.

Exit code canonici — uguali su tutti i moduli, così una pipeline CI può reagire al perché un comando si è fermato, non solo al fatto che si sia fermato:

CodiceSignificato
0tutto ok: copertura completa, niente da segnalare
1trovato qualcosa che potresti voler guardare (secret, finding, alert…)
2errore d'uso o d'input (flag sbagliato, file illeggibile o malformato)
3bloccato: il target è fuori dallo scope autorizzato (ed è stato loggato)
4rifiutato: serviva un flag di autorizzazione esplicito (--i-am-authorized) e non c'era
5parziale: l'esecuzione ha perso copertura, quindi i finding non sono esaustivi
6fallito: nulla è stato completato, il risultato non porta informazione
7annullato: l'esecuzione si è fermata su richiesta prima di finire
8engine mancante: un engine esterno obbligatorio è assente, quindi non è partito nulla (nessuna rete toccata)

I codici 5 e 6 sono ciò che permette di distinguere "abbiamo guardato ovunque e non c'era niente" da "non siamo riusciti a guardare" — vedi stato e copertura.

[http]

TipoDefaultOverride

Se qualcosa non va

  • command not found: olympus — il venv non è attivo. source .venv/bin/activate dentro

la cartella olympus-security.

  • ModuleNotFoundError o errori d'import — l'installazione non è andata a buon fine o è

stata fatta fuori dal venv. Ripeti pip install -e ".[dev]" col venv attivo.

  • blocked, out of scope (uscita 3) — comportamento previsto, non un bug: il target non

è nel file passato con --scope. Aggiungilo al JSON di scope se sei davvero autorizzato a testarlo.

  • refused: --i-am-authorized required (uscita 4) — il comando fa un lookup reale verso

terzi o un test attivo: rilancialo con --i-am-authorized solo se hai davvero l'autorizzazione documentata.

  • make check fallisce sulla coverage — mancano le dipendenze di sviluppo: assicurati di

aver installato con pip install -e ".[dev]" (non solo pip install -e .) e di avere il venv attivo.

  • Un comando che fa lookup reali non risponde/va in timeout — verifica la connessione, e

ricontrolla di aver passato uno scope che include davvero il target: senza rete i moduli offline (Hermes, Apollo, Minerva) continuano comunque a funzionare normalmente.

  • Vuoi provare Mars ma non hai Docker — non serve: python labs/mars/target/app.py avvia

il bersaglio senza Docker, come mostrato sopra.
