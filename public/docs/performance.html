Olympus performance baselines

scripts/benchmark_hot_paths.py measures four deterministic, offline paths:

ScenarioWorkload (quick)What is timed
Access-log ingest1,000 recordsParse and normalize into core.Event models
Finding deduplication2,000 inputs / 1,000 uniqueExact-ID deduplication and conflict-safe lookup
Large report rendering200 assets + 1,000 findingsBuild a canonical report and render escaped HTML
Themis queue lifecycle50 jobsInitialize SQLite, submit with idempotency keys, claim the queue

Inputs use fixed synthetic values and a fixed timestamp. No real target, external service, scanner binary, credential or repository data is used. The Themis case uses an isolated temporary database and loopback-only scope. Every scenario runs once as warm-up followed by three measured samples in the quick profile; standard uses ten times the record count (up to 10,000) and five times the queue job volume (250 jobs), with five measured samples. Compare reports only across the same profile and equivalent Python/OS environments.

Each sample records wall time, process CPU time and peak Python allocations via tracemalloc. CPU time excludes other system processes; traced memory does not include native allocator or child-process RSS. Results are diagnostic rather than a substitute for production profiling.

Streaming and backpressure

olympus apollo ingest reads, parses and writes one record at a time. The consumer controls the producer's pace; aggregate bytes, per-line bytes and line count are bounded, while skipped-record details are capped separately. Output is written to an owner-only temporary file and atomically replaces the target only after the complete input succeeds, so a malformed or growing source cannot leave a partial NDJSON artifact.

olympus apollo run likewise evaluates each unique event before reading the next. Deduplication retains only each event ID and a SHA-256 fingerprint rather than every normalized event. Alerts remain bounded by --max-alerts because they are the requested result set, not an unbounded input buffer.

Initial budgets

The initial fail thresholds below apply to the quick profile. They are intentionally broad regression guards rather than product SLOs. The --enforce mode scales time and traced-memory limits linearly with each scenario's input count for larger profiles.

Record machine, Python version, profile and commit alongside benchmark JSON. Run the same host at least three times before changing a budget; revise a limit only with an explained workload and measurements, not to hide a regression. Budgets are not yet CI blockers because shared runners have variable performance.

Single-process queue sample (2026-10-31)

--profile standard --enforce ran on Linux/Python 3.12.14 against synthetic, loopback-only fixtures at commit 1db4ac1. The Themis scenario submitted and claimed 250 jobs in five measured samples: median wall time 1.684 s, worst sample 1.779 s, median CPU 1.010 s, and peak traced Python allocation 0.019 MiB. All four benchmark scenarios remained within their configured diagnostic budgets. The queue figure is an aggregate lifecycle measurement in one process; it is not request latency, a p95, a lock-contention test or a capacity/SLO promise. DEV-E-02 remains open pending a declared Web workload, Web request latency measurements and recovery results. A separate process contention harness is available as scripts/benchmark_themis_concurrency.py; run it three times on the same host before comparing results:

python scripts/benchmark_themis_concurrency.py --processes 4 --jobs-per-process 50

On the same Linux 6.18.57 / Python 3.12.14 host at commit bf3e22d, three offline runs each submitted 200 synthetic jobs from four independent writer processes. Every run persisted all 200 rows with zero submit/SQLite errors. Elapsed times were 0.312 / 0.285 / 0.311 s; throughput 641 / 703 / 644 jobs/s; median per-submit latency 2.574 / 2.787 / 2.660 ms; nearest-rank p95 11.328 / 10.674 / 17.992 ms. These are SQLite job-store measurements, not API/Web latency, workload capacity guarantees or recovery results.

Correlation sample (2026-11-27)

The CORR-2 correlation engine (vulcan.correlate.correlate_findings, the pure offline core the CLI, API and report companion all share) was measured on Linux/Python 3.13 against a synthetic corpus — findings spread over 200 assets with overlapping CVEs, CWEs and evidence references, so every deterministic kind fires. Five samples each:

CorpusMedian wallWorst wallPeak traced memory
500 findings1.6 ms1.8 ms0.39 MiB
2000 findings9.0 ms9.5 ms1.53 MiB

The joins are bounded and near-linear in the finding count. The diagnostic budget for a 2000-finding correlation is a deliberately broad regression guard: ≤ 1.0 s wall and ≤ 32 MiB traced memory — orders of magnitude above the observation, so it catches an accidental superlinear regression without being an SLO. It is a documented baseline, not a CI blocker (shared runners vary), and the figures are one container run, not a portable promise. Re-measure when the join rules change. API/Web request latency is out of scope here; every correlate query is recorded by the API audit middleware regardless of timing.
